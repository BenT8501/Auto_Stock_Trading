## 3. 성과 — 쌓은 경험과 지식

<u>Unreal Engine의 Server RPC 호출 조건과 실행 방식을 익혔습니다. 소유 Controller·Pawn을 통해 팀 선택·발사·재장전 요청을 서버에 전달하고, 서버에서 조건을 검사·처리하는 흐름을 구현했습니다.</u>

<u>Unreal Engine의 변수 복제 설정과 RepNotify 사용 방법을 익혔습니다. 탄약은 클라이언트에 복제된 값을 HUD에서 조회하고, 무기 정보는 OnRep에서 기존 외형 갱신 함수를 호출하도록 연결했습니다.</u>

<u>Listen Server 환경에서 접속부터 경기 진행·종료, 재경기와 재접속까지 이어지는 멀티플레이 흐름을 구현했습니다.</u>

### 5-1. 아키텍처 구현을 통한 역량 향상

**수행 내용**

- <u>Listen Server 접속과 팀 선택을 연결하고, GameMode·GameState·PlayerState·PlayerController·Character에 서버 처리와 복제 데이터를 배치.</u>
- <u>서버 요청·상태 복제·클라이언트 후속 처리를 연결하고, 엔진 제공 기능과 프로젝트에서 작성한 로직 구분.</u>

**Unreal Engine 제공 기능**

- <u>Listen Server: 호스트가 게임 서버와 플레이를 함께 실행하는 네트워크 모드.</u>
- <u>OpenLevel의 listen 옵션과 ClientTravel: 서버 실행·서버 주소 접속에 사용.</u>
- <u>PlayerController·Pawn·PlayerState·GameMode·GameState: 플레이어 제어·게임 규칙·공유 상태를 구성하는 프레임워크.</u>
- <u>HasAuthority·IsLocallyControlled·IsLocalController: 서버 실행과 로컬 입력·UI 처리를 구분하는 확인 함수.</u>

**주요 클래스 및 함수**

**팀 선택·입장 흐름**

<pre><u>호스트: HostMatch → OpenLevel(listen)</u>
<u>게스트: JoinMatch → ClientTravel(호스트 주소)</u>
<u>→ 엔진 접속 처리·Controller/PlayerState 준비</u>
→ 로컬 팀 선택 UI
→ RequestTeamSelection → ServerRequestTeamSelection

→ PlayerState::SetPlayerTeam
→ 팀 주변 위치 탐색·Pawn 생성·Possess

→ HUD 생성·게임 입력 전환</pre>

<u>접속·소유 연결 자체는 엔진이 처리하고, 팀 미선택 상태의 생성 보류·팀 승인·위치 탐색·UI 전환은 프로젝트에서 구현했습니다. 소유 클라이언트가 자신의 Controller·Pawn에서 Server RPC를 요청하도록 구성했으며, 서버 소유 아이템을 클라이언트가 직접 변경하는 방식으로 구현하지 않았습니다. [Unreal Engine 소유 연결 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/actor-owner-and-owning-connection-in-unreal-engine?application_version=5.7)</u>

**Unreal Engine 제공 기능과 적용**

| <u>기능</u> | <u>현재 코드에서 사용한 예</u> | <u>의미</u> |
|---|---|---|
| <u>Server RPC</u> | <u>ServerRequestFire, ServerRequestReload, ServerRequestWeaponPickup, ServerSetRunning</u> | <u>소유 클라이언트가 서버에서 실행할 처리 요청</u> |
| <u>Client RPC</u> | <u>ClientTeamSelectionResult, ClientPrepareNewMatch</u> | <u>서버가 해당 플레이어의 클라이언트에 결과·초기화 안내</u> |
| <u>NetMulticast RPC</u> | <u>MulticastPlayAttackAnimation, MulticastSetReloadAnimation</u> | <u>서버와 해당 Actor를 전달받는 클라이언트에서 애니메이션 재생·정지 실행</u> |
| <u>Reliable</u> | <u>발사·재장전·달리기 등 서버 요청, 재장전 애니메이션 호출</u> | <u>전송 누락 시 재전송하는 전달 방식</u> |
| <u>Unreliable</u> | <u>공격 애니메이션 Multicast</u> | <u>유실된 호출을 재전송하지 않는 방식</u> |
| <u>Replicated / ReplicatedUsing</u> | <u>탄약, 현재 무기, 쉴드, 사망·팀 상태</u> | <u>서버 변수의 변경값을 클라이언트 대응 객체에 반영</u> |
| <u>GetLifetimeReplicatedProps·DOREPLIFETIME</u> | <u>Character·PlayerState·GameState 변수 등록</u> | <u>어떤 변수를 복제할지 엔진에 등록</u> |

<u>RPC와 그 전달·실행 기능은 Unreal Engine 제공 기능이며, 프로젝트에서는 호출 시점·인자·검사·결과 처리를 구현했습니다. Reliable은 게임 로직의 성공을 보장하지 않으며, 서버에서 사망·탄약 등 조건에 따라 요청을 거절할 수 있습니다. [Unreal Engine RPC 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine?application_version=5.7)</u>

**데이터 저장·반영 경로**

| 저장 위치 | 변수·속성 | <u>클라이언트 반영</u> |
|---|---|---|

| ZCharacterBaseMulti | currentAmmo | <u>변수 복제 후 상태 HUD에서 조회</u> |

<u>HP는 `UZAttributeSet` 속성으로 보관하고, `DOREPLIFETIME_CONDITION_NOTIFY`와 `GAMEPLAYATTRIBUTE_REPNOTIFY`로 복제·변경 알림을 연결했습니다. FPS 피해는 서버의 ReceivePlayerDamage에서 HP를 변경합니다.</u>

<u>변수 복제는 변경마다 즉시 모든 중간값을 전달하는 방식이 아닙니다. 네트워크 갱신에 따라 최신 상태가 반영되므로, 빠른 연속 변경의 중간값은 생략될 수 있습니다. [Unreal Engine 변수 복제 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/property-replication-in-unreal-engine?application_version=5.2)</u>

- <u>클라이언트가 직접 GameMode를 호출하는 대신 소유 Controller·Pawn의 RPC로 서버 실행을 요청하는 방법 적용.</u>
- <u>접속 완료, 팀 승인, Pawn 생성, 로컬 화면 준비를 별도 단계로 구분.</u>
- <u>Reliable RPC 전달 보장과 서버 로직의 승인 여부를 구분.</u>

### 5-2. 전투·투사체 구현을 통한 역량 향상

**수행 내용**

**발사·피해 흐름**

```text
FPS Fire → ServerRequestFire → FirePrimaryProjectile
→ 서버 권한·생존·종료·재장전·데이터·탄약·발사 간격 검사
→ 풀에서 Projectile 획득·피해·속도·방향 설정
→ 서버 발사체 충돌·장애물·중복 피격 검사
→ ReceivePlayerDamage에서 팀 관계 확인
→ 쉴드 우선 차감·초과분 HP 적용
→ 사망·팀 점수·리스폰
```

**발사체 복제·재사용과 애니메이션 처리**

- <u>발사체는 bReplicates와 SetReplicateMovement를 설정하고, 재사용 활성 상태는 bProjectileActive·OnRep_ProjectileActive로 반영.</u>
- <u>풀의 획득·반환과 동일 대상 중복 피해를 막는 RuntimeHitActors는 프로젝트 코드. 객체 재사용 시 피격 기록·타이머·이동 등을 정리.</u>
- <u>조준 방향과 장애물 추가 확인에는 Trace 사용. 실제 피해 기준은 서버 Projectile 충돌이며 계획의 Hitscan 방식에서 변경.</u>
- <u>공격 표현은 Unreliable Multicast, 재장전 재생·정지는 Reliable Multicast 사용. 애니메이션 실행과 실제 탄약·피해 결과를 구분.</u>
- <u>재장전은 서버 타이머의 ComplateServerReload에서 탄약 확정. 사망·다른 무기로 교체 시 기존 타이머·진행 상태 취소.</u>

**발사 성공 후 공격 표현·탄약·HUD 반영**

<u>발사 입력을 Server RPC로 전달하고, 서버에서 생존·경기 종료·재장전·탄약·발사 간격을 검사한 뒤 발사체를 실행했습니다. 발사 성공 시 공격 애니메이션은 Multicast RPC로 실행하고, 서버에서 차감한 탄약은 변수 복제로 클라이언트 캐릭터에 반영했습니다. HUD는 Tick에서 소유 캐릭터의 탄약을 조회해 표시하도록 구성했습니다.</u>

**이동·달리기 구현과 게스트 오류 수정**

**활용한 Unreal Engine 기능**

<u>기본 이동·점프는 CharacterMovement를 사용했습니다. 엔진이 소유 클라이언트의 이동 예측, 서버 이동 처리·보정, 다른 클라이언트의 이동 표현을 처리합니다. 프로젝트에서 해당 이동 전송·예측 시스템을 새로 만든 것은 아닙니다. [Unreal Engine CharacterMovement 네트워크 이동 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine?application_version=5.7)</u>

**직접 추가·수정한 내용**

<pre><u>게스트의 Shift 입력
→ 로컬 ApplyRunningState(true): MaxWalkSpeed 변경
→ ServerSetRunning(true): 서버에 달리기 여부 전달
→ 서버 ServerSetRunning_Implementation: 사망 상태이면 달리기 해제
→ 서버 ApplyRunningState: bIsRunning·MaxWalkSpeed 적용

Shift 해제·취소
→ 로컬 걷기 속도 적용
→ ServerSetRunning(false)
→ 서버 걷기 속도 적용</u></pre>

<u>`bRunning`은 RPC 인자이며, 로컬·서버 각 인스턴스의 `bIsRunning`과 MaxWalkSpeed를 설정합니다. 호스트의 로컬 캐릭터는 이미 서버에서 실행되므로 ApplyRunningState를 직접 적용합니다. 속도 숫자를 모든 클라이언트에 Multicast하거나 bIsRunning 변수를 복제한 구현이 아닙니다.</u>

**게스트 달리기 수정**

<u>게스트의 로컬 속도 변경만으로 서버의 최대 이동 속도가 바뀌지 않는 문제를 확인했습니다. 달리기 시작·종료 상태를 서버로 전달해 서버에서도 적용하도록 수정했습니다. 별도 RPC 방식으로 구현했으며, SavedMove·압축 플래그를 확장한 구현은 아닙니다.</u>

**무기 습득·교체**

| 기능 | 실제 처리 |
|---|---|
| 무기 습득 | <u>클라이언트 요청 → 소유 캐릭터 Server RPC → 서버에서 생존·종료·아이템·실제 Overlap 검사 → 장착 성공 시 Destroy</u> |
| 동일 무기 | 동일 Data Asset 기준 기본 공격력의 10%씩 최대 3회 강화·탄약 유지, 최대 강화면 미소비 |
| 다른 무기 | 이전 강화 초기화, 새 무기 데이터·기본 탄약 적용 |

**향상된 실무 역량**

- <u>클라이언트 요청과 서버의 충돌·타이머 실행을 구분해 전투 결과를 결정하는 흐름 구성.</u>
- <u>발사 요청은 Server RPC, 공격 표현은 Multicast RPC, 탄약은 변수 복제와 HUD 조회로 연결하는 경험.</u>
- <u>기존 풀을 서버 발사에 활용하고, 샷건 발사체 간 충돌로 즉시 반환되는 경로 확인·수정.</u>

### 5-3. UI·상호작용 구현을 통한 역량 향상

**수행 내용과 주요 UI 클래스·함수**

| 클래스·함수 | 데이터 연결·화면 처리 |
|---|---|
| MultiPlayerController::CreateHUDWidget | 소유 플레이어의 Widget 생성·보관, 경기 단계에 따른 화면 전환·입력 모드 설정 |
| UZStateHUDWidget::RefreshCurrentStatus | 소유 Pawn의 HP·쉴드·탄약·무기 정보를 조회하여 위젯 값 갱신 |
| UZTeamStatusWidget::RefreshTeamStatus | 로컬 PlayerState의 팀과 GameState의 점수·남은 시간 조회·표시 |
| FPS의 Attribute 변경 알림·HP Bar | 피해 시 해당 대상 HP Bar 표시, 마지막 피격부터 3초 후 숨김 |
| FPS::UpdateTeamMarkerPresentation | 팀 관계와 시야 차폐를 확인하여 마커 표시 조정 |

<u>서버에서 Widget을 만들어 각 클라이언트에 보내는 대신, 각 로컬 화면에서 복제된 캐릭터·PlayerState·GameState의 값을 읽도록 연결했습니다. 상태 HUD·팀 HUD는 Tick에서 값을 조회하고, 무기 외형·HP Bar 등은 OnRep·Attribute 변경 알림을 함께 사용합니다. Controller는 위젯의 생성·전환을 처리하고, 개별 위젯은 조회한 값을 화면 요소에 표시합니다.</u>

**무기 교체 후 서버·클라이언트 외형 갱신**

<u>서버에서 현재 무기 정보를 변경한 뒤 무기 메시·애니메이션 갱신을 직접 실행하고, 클라이언트는 OnRep_CurrentWeaponData에서 같은 갱신을 실행하도록 연결했습니다. C++ 서버의 값 변경만으로 서버 OnRep가 자동 호출되지는 않으므로, 서버의 직접 갱신과 클라이언트의 복제 알림을 구분해 구현했습니다.</u>

**아이템 생성·소비**

| 기능 | 실제 처리 |
|---|---|
| 쉴드 습득 | <u>서버에서 등록한 Overlap → RestoreShield → 실제 회복 성공 시 Destroy. 별도의 클라이언트 습득 RPC를 호출하지 않음</u> |
| 픽업 보충 | 서버가 무기·쉴드 종류를 선택·생성하고, 소비된 지점만 기본 10초 후 재생성 |

<u>공격·재장전·무기 습득은 요청 RPC를 사용하지만, 모든 기능을 같은 RPC 경로로 묶지는 않았습니다. 충돌·Overlap·타이머 등 서버에서 이미 확인한 사건은 해당 서버 코드에서 처리했습니다.</u>

**향상된 실무 역량**

- <u>상태값이 저장·복제되는 위치와 화면에 표시되는 위치를 구분하여 연결.</u>
- <u>값 조회 방식과 변경 알림 방식을 실제 UI에 적용하고, Pawn 준비 전에는 화면 전환을 보류하도록 구성.</u>
- <u>서버의 직접 표현 갱신과 클라이언트 OnRep 갱신을 구분하여 구현.</u>

### 5-4. 경기 진행·리스폰 구현을 통한 역량 향상

**수행 내용과 Unreal Engine 기능 활용**

- <u>엔진의 Pawn 생성·Possess와 PlayerState를 사용하고, 팀 저장 위치·리스폰 지연·스폰 탐색·경기 단계는 직접 구성.</u>
- <u>팀 선택 승인과 Pawn 생성은 별도 처리. 위치가 점유돼 있으면 주변 탐색, 공간이 없으면 접속과 팀을 유지하며 기본 0.5초 간격 재시도.</u>
- <u>경기 상태는 프로젝트 enum의 Waiting·Playing·Finished 사용. AGameModeBase 위에서 직접 구성한 단계이며 AGameMode 내장 MatchState를 그대로 사용한 구현은 아님.</u>
- <u>일반 리스폰에서는 팀 유지, 전체 재경기에서는 팀을 None으로 초기화해 다시 선택.</u>

**사망 후 Pawn 교체·팀 유지·전투 값 초기화**

<u>서버의 GameMode에서 사망 후 리스폰을 예약하고, 지연 시간이 지나면 기존 Pawn을 제거한 뒤 새 캐릭터를 생성하도록 구현했습니다. 소속 팀은 PlayerState에 유지해 같은 팀의 스폰 위치를 사용하고, HP·탄약은 새 Pawn에서 초기화했습니다. 이를 통해 Unreal Engine의 Pawn·PlayerState 수명 차이에 맞춰 유지할 정보와 초기화할 정보를 배치하는 경험을 쌓았습니다.</u>

**재경기 흐름**

<pre><u>호스트의 재경기 요청
→ 서버에서 경기·플레이어 상태 초기화
→ 클라이언트에서 이번 초기화 상태 검사 후 준비 완료 응답
→ 준비 응답 대기 없음 + 양 팀 인원 존재 시 경기 시작</u></pre>

**클라이언트 준비 응답과 서버의 경기 시작 조건**

<u>서버가 Client RPC로 재경기를 안내하면, 클라이언트는 GameState·PlayerState·Pawn의 초기화 상태를 검사한 뒤 Server RPC로 준비 완료를 전달하도록 구현했습니다. 이번 초기화 번호와의 일치 여부, 경기 종료 해제, 팀 미선택, 기존 Pawn 제거를 준비 조건으로 사용했습니다.</u>

<u>서버는 응답 번호를 검사하고, 준비 응답을 기다리는 플레이어가 없으며 양 팀에 인원이 있을 때 경기를 시작합니다. 경기 시작 조건에 모든 Pawn의 스폰 완료 검사는 포함하지 않았습니다. 이전 경기에서 예약한 리스폰 작업도 다음 경기에 실행되지 않도록 구분했습니다.</u>

<u>이 과정에서 Unreal Engine의 RPC 수신과 관련 객체의 상태 반영 완료를 구분하고, 다음 처리를 시작할 조건을 구성하는 경험을 쌓았습니다. [Unreal Engine 복제 실행 순서 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/replicated-object-execution-order-in-unreal-engine?application_version=5.7)</u>

**향상된 실무 역량**

- <u>Client RPC 수신과 GameState·PlayerState·Pawn 상태 반영을 구분하고, 초기화 번호 검사·준비 응답으로 재경기 시작 조건 구성.</u>
- <u>일반 리스폰 시 PlayerState의 팀을 유지하고 새 Pawn의 HP·탄약을 초기화하는 데이터 배치·생성 흐름 구성.</u>
- <u>팀 승인·위치 탐색·Pawn 생성을 나누어 실패 원인 확인. 위치 점유로 생성하지 못한 경우 팀 승인을 유지하면서 서버에서 재시도하도록 구성.</u>
