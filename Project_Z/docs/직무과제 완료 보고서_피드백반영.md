## 2. 진행 결과 — 계획 대비 실제 달성 내용

### 개발 목표

- 기존 Unity 멀티플레이 경험을 Unreal의 클래스 구조·서버 실행·상태 복제 방식에 적용.
- UE5가 제공하는 네트워크 기능을 활용해 접속·팀 선택·이동·전투·리스폰 구현.
- 각 기능의 실행 위치와 데이터 전달 과정을 확인하고, 구현 내용과 오류 수정 근거를 설명.

### 실제 구현 환경과 범위

- Unreal Engine 5.7, C++, Blueprint·데이터 에셋 사용.
- UE5의 **Listen Server**로 호스트가 서버와 로컬 플레이어를 함께 실행하고, 게스트가 호스트 주소에 접속하는 방식.
- UE5의 접속 처리, Actor 복제, RPC, CharacterMovement, GameMode·GameState·PlayerState를 활용.
- 기존 Project_Z의 캐릭터·무기·발사체·풀을 활용하고, 서버 검사·데이터 전달·팀 경기·재경기 처리를 추가·수정.
- 최대 6인 목표의 Team A/B FPS 구성. 별도 전용 서버나 자체 소켓·패킷 전송 계층을 개발한 과제가 아님.

## 3. 성과 — 쌓은 경험과 지식

RPC와 서버 요청 처리 개념은 기존 개발 경험을 통해 알고 있었으며, 이번 과제에서는 이를 Unreal의 Server RPC로 연결하는 방법을 익혔습니다. 특히 소유 Controller·Pawn을 통한 호출 조건과 서버에서 처리 함수가 실행되는 방식을 확인했습니다.

Unreal의 변수 복제 등록과 OnRep를 활용해 서버에서 변경한 값을 클라이언트에 반영하고, HUD·무기 외형을 갱신하는 방법을 익혔습니다. 기존에 사용하던 데이터 수신·화면 갱신 방식을 UE5의 복제 기능과 로컬 조회 방식에 맞춰 적용했습니다.

UE5의 네트워크 기능을 활용해 접속·팀 선택·전투·리스폰·경기 종료·재경기·퇴장 및 재접속을 연결하고 동작을 확인했습니다. 엔진이 제공하는 처리와 프로젝트에서 추가한 로직을 구분하고, 실행 위치와 데이터 전달 흐름을 설명할 수 있도록 정리했습니다.

## 5. 업무결과 — UE5 제공 기능과 구현 내용

### 5-1. 접속·실행 위치·클래스 구성

**UE5 제공 기능**

- Listen Server: 호스트가 게임 서버와 플레이를 함께 실행하는 네트워크 모드.
- OpenLevel의 listen 옵션과 ClientTravel: 서버 실행·서버 주소 접속에 사용.
- PlayerController·Pawn·PlayerState·GameMode·GameState: 플레이어 제어·게임 규칙·공유 상태를 구성하는 프레임워크.
- HasAuthority·IsLocallyControlled·IsLocalController: 서버 실행과 로컬 입력·UI 처리를 구분하는 확인 함수.

**직접 구현한 내용**

| 클래스 | 서버·클라이언트에서 수행하는 내용 |
|---|---|
| `AProject_Z_MultiPlayerController` | HostMatch·JoinMatch로 실행·접속, 팀 선택 서버 요청, 로컬 Widget 생성·전환·입력 모드 설정 |
| `AProject_Z_MultiGameMode` | 서버에서 팀 승인·스폰·리스폰·점수 등록·경기 종료·재경기 실행 |
| `AProject_Z_MultiGameState` | 서버의 팀 점수·시간·경기 단계·승리 팀·초기화 번호 저장·복제 |
| `AProject_Z_MultiPlayerState` | 승인된 팀 보관·복제, 일반 리스폰 후 팀 유지 |
| `AZCharacterBase` | ASC·AttributeSet 생성, Ability Actor 정보 초기화, 속성 조회 함수 제공 |
| `AZCharacterBaseMulti` | 서버 전투 처리, 탄약·쉴드·무기·사망 상태 복제. ASC 복제 설정과 HP Attribute 복제 연결 |
| `AZCharacter_FPS` | FPS 입력·카메라·조준, 달리기·재장전 RPC, 무기 습득 조건과 로컬 HP Bar·마커 연결 |

캐릭터 상속은 `ZCharacterBase → ZCharacterBaseMulti → ZCharacter_FPS / ZCharacter_TPS`로 구성했습니다. 기존 TPS 코드는 유지하면서 공통 전투를 Multi에 모으고 FPS 입력·표현을 추가했습니다.

**팀 선택·입장 흐름**

```text
호스트: HostMatch → OpenLevel(listen)
게스트: JoinMatch → ClientTravel(호스트 주소)
→ 엔진 접속 처리·Controller/PlayerState 준비
→ 로컬 팀 선택 UI
→ RequestTeamSelection → ServerRequestTeamSelection
→ GameMode::TrySelectPlayerTeam
→ PlayerState::SetPlayerTeam
→ 팀 주변 위치 탐색·Pawn 생성·Possess
→ 로컬 팀·Pawn 준비 확인
→ HUD 생성·게임 입력 전환
```

접속·소유 연결 자체는 엔진이 처리하고, 팀 미선택 상태의 생성 보류·팀 승인·위치 탐색·UI 전환은 프로젝트에서 구현했습니다. 소유 클라이언트가 자신의 Controller·Pawn에서 Server RPC를 요청하도록 구성했으며, 서버 소유 아이템을 클라이언트가 직접 변경하는 방식으로 구현하지 않았습니다. [UE5 소유 연결 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/actor-owner-and-owning-connection-in-unreal-engine?application_version=5.7)

**쌓은 지식·경험**

- HasAuthority는 서버 권한 확인, 로컬 제어 확인은 입력·화면 처리 여부 확인이라는 차이 파악.
- 클라이언트가 직접 GameMode를 호출하는 대신 소유 Controller·Pawn의 RPC로 서버 실행을 요청하는 방법 적용.
- 접속 완료, 팀 승인, Pawn 생성, 로컬 화면 준비를 별도 단계로 구분.

### 5-2. RPC·변수 복제·표현 갱신

**UE5 제공 기능과 적용**

| 기능 | 현재 코드에서 사용한 예 | 의미 |
|---|---|---|
| Server RPC | ServerRequestFire, ServerRequestReload, ServerRequestWeaponPickup, ServerSetRunning | 소유 클라이언트가 서버에서 실행할 처리 요청 |
| Client RPC | ClientTeamSelectionResult, ClientPrepareNewMatch | 서버가 해당 플레이어의 클라이언트에 결과·초기화 안내 |
| NetMulticast RPC | MulticastPlayAttackAnimation, MulticastSetReloadAnimation | 서버와 해당 Actor를 전달받는 클라이언트에서 애니메이션 재생·정지 실행 |
| Reliable | 발사·재장전·달리기 등 서버 요청, 재장전 애니메이션 호출 | 전송 누락 시 재전송하는 전달 방식 |
| Unreliable | 공격 애니메이션 Multicast | 유실된 호출을 재전송하지 않는 방식 |
| Replicated / ReplicatedUsing | 탄약, 현재 무기, 쉴드, 사망·팀 상태 | 서버 변수의 변경값을 클라이언트 대응 객체에 반영 |
| GetLifetimeReplicatedProps·DOREPLIFETIME | Character·PlayerState·GameState 변수 등록 | 어떤 변수를 복제할지 엔진에 등록 |

RPC와 그 전달·실행 기능은 UE5 제공 기능이며, 프로젝트에서는 호출 시점·인자·검사·결과 처리를 구현했습니다. Reliable은 게임 로직의 성공을 보장하지 않으며, 서버에서 사망·탄약 등 조건에 따라 요청을 거절할 수 있습니다. [UE5 RPC 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine?application_version=5.7)

**데이터 저장·반영 경로**

| 저장 위치 | 변수·속성 | 클라이언트 반영 |
|---|---|---|
| 캐릭터의 AttributeSet | HP·MaxHP | Attribute 복제·변경 알림, HUD 조회·피격 HP Bar 갱신 |
| ZCharacterBaseMulti | currentAmmo | 변수 복제 후 상태 HUD에서 조회 |
| ZCharacterBaseMulti | CurrentShield·MaxShield | 복제된 값 조회, OnRep에서 보호막 표현 갱신 |
| ZCharacterBaseMulti | CurrentWeaponData | OnRep_CurrentWeaponData에서 무기 메시·애니메이션 갱신 |
| MultiPlayerState | PlayerTeam | OnRep_PlayerTeam에서 팀 변경 알림 |
| MultiGameState | TeamAScore·TeamBScore·RemainingMatchSeconds·MatchPhase·WinningTeam | 해당 클라이언트의 GameState 갱신 후 팀 HUD·결과 UI에서 조회 |

HP는 `UZAttributeSet` 속성으로 보관하고, `DOREPLIFETIME_CONDITION_NOTIFY`와 `GAMEPLAYATTRIBUTE_REPNOTIFY`로 복제·변경 알림을 연결했습니다. FPS 피해는 서버의 ReceivePlayerDamage에서 HP를 변경합니다.

**화면 갱신 사례**

서버에서 탄약을 30에서 29로 변경하면, 클라이언트의 해당 캐릭터 탄약 변수에 변경값이 반영되고 HUD가 이를 읽어 표시합니다. 무기 교체 시에는 서버가 CurrentWeaponData를 변경한 뒤 외형 갱신 함수를 직접 호출하고, 클라이언트는 OnRep_CurrentWeaponData에서 외형을 갱신합니다. C++ 서버에서 값을 바꾸는 것만으로 서버 OnRep가 자동 호출되지는 않습니다.

변수 복제는 변경마다 즉시 모든 중간값을 전달하는 방식이 아닙니다. 네트워크 갱신에 따라 최신 상태가 반영되므로, 빠른 연속 변경의 중간값은 생략될 수 있습니다. [UE5 변수 복제 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/property-replication-in-unreal-engine?application_version=5.2)

**쌓은 지식·경험**

- 함수 실행 요청과 현재 상태 전달을 구분하고 Server·Client·Multicast RPC와 변수 복제를 실제 기능에 연결.
- Reliable RPC 전달 보장과 서버 로직의 승인 여부를 구분.
- 서버의 직접 표현 갱신과 클라이언트 OnRep 갱신을 구분하여 구현.

### 5-3. 기본 이동과 게스트 달리기 수정

**UE5 제공 기능**

기본 이동·점프는 CharacterMovement를 사용했습니다. 엔진이 소유 클라이언트의 이동 예측, 서버 이동 처리·보정, 다른 클라이언트의 이동 표현을 처리합니다. 프로젝트에서 해당 이동 전송·예측 시스템을 새로 만든 것은 아닙니다. [UE5 CharacterMovement 네트워크 이동 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine?application_version=5.7)

**직접 추가·수정한 내용**

```text
게스트의 Shift 입력
→ 로컬 ApplyRunningState(true): MaxWalkSpeed 변경
→ ServerSetRunning(true): 서버에 달리기 여부 전달
→ 서버 ServerSetRunning_Implementation: 사망 상태이면 달리기 해제
→ 서버 ApplyRunningState: bIsRunning·MaxWalkSpeed 적용

Shift 해제·취소
→ 로컬 걷기 속도 적용
→ ServerSetRunning(false)
→ 서버 걷기 속도 적용
```

`bRunning`은 RPC 인자이며, 로컬·서버 각 인스턴스의 `bIsRunning`과 MaxWalkSpeed를 설정합니다. 호스트의 로컬 캐릭터는 이미 서버에서 실행되므로 ApplyRunningState를 직접 적용합니다. 속도 숫자를 모든 클라이언트에 Multicast하거나 bIsRunning 변수를 복제한 구현이 아닙니다.

**게스트 달리기 수정**

게스트의 로컬 속도 변경만으로 서버의 최대 이동 속도가 바뀌지 않는 문제를 확인했습니다. 달리기 시작·종료 상태를 서버로 전달해 서버에서도 적용하도록 수정했습니다. 별도 RPC 방식으로 구현했으며, SavedMove·압축 플래그를 확장한 구현은 아닙니다.

### 5-4. 서버 전투·무기·픽업 구현

**발사·피해 흐름**

```text
FPS Fire → ServerRequestFire → FirePrimaryProjectile
→ 서버 권한·생존·종료·재장전·데이터·탄약·발사 간격 검사
→ 풀에서 Projectile 획득·피해·속도·방향 설정
→ 서버 발사체 충돌·장애물·중복 피격 검사
→ ReceivePlayerDamage에서 팀 관계 확인
→ 쉴드 우선 차감·초과분 HP 적용
→ 사망·팀 점수·리스폰
```

**발사체 복제·재사용과 애니메이션 처리**

- 발사체는 bReplicates와 SetReplicateMovement를 설정하고, 재사용 활성 상태는 bProjectileActive·OnRep_ProjectileActive로 반영.
- 풀의 획득·반환과 동일 대상 중복 피해를 막는 RuntimeHitActors는 프로젝트 코드. 객체 재사용 시 피격 기록·타이머·이동 등을 정리.
- 조준 방향과 장애물 추가 확인에는 Trace 사용. 실제 피해 기준은 서버 Projectile 충돌이며 계획의 Hitscan 방식에서 변경.
- 공격 표현은 Unreliable Multicast, 재장전 재생·정지는 Reliable Multicast 사용. 애니메이션 실행과 실제 탄약·피해 결과를 구분.
- 재장전은 서버 타이머의 ComplateServerReload에서 탄약 확정. 사망·다른 무기로 교체 시 기존 타이머·진행 상태 취소.

**아이템별 실행 경로**

| 기능 | 실제 처리 |
|---|---|
| 무기 습득 | 클라이언트 요청 → 소유 캐릭터 Server RPC → 서버에서 생존·종료·아이템·실제 Overlap 검사 → 장착 성공 시 Destroy |
| 동일 무기 | 동일 Data Asset 기준 기본 공격력의 10%씩 최대 3회 강화·탄약 유지, 최대 강화면 미소비 |
| 다른 무기 | 이전 강화 초기화, 새 무기 데이터·기본 탄약 적용 |
| 쉴드 습득 | 서버에서 등록한 Overlap → RestoreShield → 실제 회복 성공 시 Destroy. 별도의 클라이언트 습득 RPC를 호출하지 않음 |
| 픽업 보충 | 서버가 무기·쉴드 종류를 선택·생성하고, 소비된 지점만 기본 10초 후 재생성 |

공격·재장전·무기 습득은 요청 RPC를 사용하지만, 모든 기능을 같은 RPC 경로로 묶지는 않았습니다. 충돌·Overlap·타이머 등 서버에서 이미 확인한 사건은 해당 서버 코드에서 처리했습니다.

**쌓은 지식·경험**

- 클라이언트 요청과 서버의 충돌·타이머 실행을 구분해 전투 결과를 결정하는 흐름 구성.
- 상태값 전달과 일회성 애니메이션 실행을 다른 방법으로 연결.
- 기존 풀을 서버 발사에 활용하고, 샷건 발사체 간 충돌로 즉시 반환되는 경로 확인·수정.

### 5-5. 리스폰·경기 전환·재경기

**UE5 기능과 직접 구현의 구분**

- 엔진의 Pawn 생성·Possess와 PlayerState를 사용하고, 팀 저장 위치·리스폰 지연·스폰 탐색·경기 단계는 직접 구성.
- 팀 선택 승인과 Pawn 생성은 별도 처리. 위치가 점유돼 있으면 주변 탐색, 공간이 없으면 접속과 팀을 유지하며 기본 0.5초 간격 재시도.
- 경기 상태는 프로젝트 enum의 Waiting·Playing·Finished 사용. AGameModeBase 위에서 직접 구성한 단계이며 AGameMode 내장 MatchState를 그대로 사용한 구현은 아님.
- 일반 리스폰에서는 팀 유지, 전체 재경기에서는 팀을 None으로 초기화해 다시 선택.

**재경기 흐름**

```text
호스트 Restart → Controller::RestartMatch
→ GameMode::RestartMatchForHost
→ 기존 타이머·발사체·픽업·Pawn·팀 정리
→ GameState 점수·시간·승리 팀 초기화, MatchResetSerial 증가
→ 각 Controller에 ClientPrepareNewMatch 전달
→ 클라이언트가 초기화 번호·팀 None·Pawn 없음 확인
→ ServerConfirmMatchResetReady 응답
→ 준비 응답 대기 없음 + 양 팀 인원 존재 시 경기 시작
```

이 준비 확인은 엔진이 모든 초기화를 자동 완료해 주는 기능이 아니라, RPC·복제를 활용해 프로젝트에서 추가한 절차입니다. 서버 초기화 함수의 종료와 클라이언트의 상태 반영 완료를 구분했습니다. RPC와 서로 다른 객체의 복제 완료 순서를 임의로 가정하지 않는 처리입니다. [UE5 복제 실행 순서 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/replicated-object-execution-order-in-unreal-engine?application_version=5.7)

MatchGeneration은 이전 경기에서 예약한 서버 리스폰 콜백을 무효화하고, MatchResetSerial은 클라이언트가 이번 초기화를 반영했는지 확인하는 데 사용합니다. 현재 시작 조건은 팀 인원과 초기화 준비 응답이며, 모든 Pawn의 스폰 완료까지 기다리는 조건은 아닙니다.

**쌓은 지식·경험**

- 서버·클라이언트의 데이터 반영 시점 차이를 고려해 초기화 번호와 준비 확인을 다음 경기의 실행 조건에 적용.
- 일반 리스폰·접속 종료·재경기에서 유지할 객체와 초기화할 값을 구분.
- 팀 승인·위치 탐색·Pawn 생성을 나누어 실패 원인 확인. 위치 점유로 생성하지 못한 경우 팀 승인을 유지하면서 서버에서 재시도하도록 구성.

### 5-6. 복제 데이터와 로컬 UI 연결

**직접 구현한 내용**

| 클래스·함수 | 데이터 연결·화면 처리 |
|---|---|
| MultiPlayerController::CreateHUDWidget | 소유 플레이어의 Widget 생성·보관, 경기 단계에 따른 화면 전환·입력 모드 설정 |
| UZStateHUDWidget::RefreshCurrentStatus | 소유 Pawn의 HP·쉴드·탄약·무기 정보를 조회하여 위젯 값 갱신 |
| UZTeamStatusWidget::RefreshTeamStatus | 로컬 PlayerState의 팀과 GameState의 점수·남은 시간 조회·표시 |
| FPS의 Attribute 변경 알림·HP Bar | 피해 시 해당 대상 HP Bar 표시, 마지막 피격부터 3초 후 숨김 |
| FPS::UpdateTeamMarkerPresentation | 팀 관계와 시야 차폐를 확인하여 마커 표시 조정 |

서버에서 Widget을 만들어 각 클라이언트에 보내는 대신, 각 로컬 화면에서 복제된 캐릭터·PlayerState·GameState의 값을 읽도록 연결했습니다. 상태 HUD·팀 HUD는 Tick에서 값을 조회하고, 무기 외형·HP Bar 등은 OnRep·Attribute 변경 알림을 함께 사용합니다. Controller는 위젯의 생성·전환을 처리하고, 개별 위젯은 조회한 값을 화면 요소에 표시합니다.

**쌓은 지식·경험**

- 상태값이 저장·복제되는 위치와 화면에 표시되는 위치를 구분하여 연결.
- 값 조회 방식과 변경 알림 방식을 실제 UI에 적용하고, Pawn 준비 전에는 화면 전환을 보류하도록 구성.
