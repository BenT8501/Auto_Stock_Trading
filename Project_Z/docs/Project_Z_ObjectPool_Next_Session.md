## 집중 보완할 내용

1. 클래스와 인스턴스: 클래스별 Pool, 같은 클래스의 서로 다른 Actor, 동일 Actor 재사용의 차이.
2. 포인터 동일성과 유효성: 같은 주소·non-null만으로 사용 가능성을 보장하지 않음. 파괴 상태와 World 소속 확인.
3. 객체 수명: 숨김과 Destroy의 차이, World 종료, WorldSubsystem과 GameInstanceSubsystem 수명 차이.
4. Pool 자료구조: Pools, AvailableActors, InUseActors, ActorToPoolClass의 책임과 상태 전환.
5. Acquire: 대기 Actor 획득, 대기 목록이 비었을 때 생성 시도, 최종 획득 실패의 구분.
6. Release: 사용 중 목록 제거, 대기 등록, 중복 반환 방어 및 제거 결과 확인.
7. 재사용 초기화: 피해량, 관통, 타격 목록, Owner, 속성, 이동, Timer, Tick, 충돌, 가시성.
8. 활성화 순서: 상태 설정 완료 전에 충돌을 켰을 때의 위험. 실제 호출 순서를 읽어 검증.
9. Timer: 반환 시 정리, 재발사 수명, 이전 콜백과 새 설정 오류의 구분. 발사 회차와 등록·해제·실행 시각 로그.
10. 검증: 같은 Actor 반환·재획득 입증과 새 상태 적용 확인은 별개. 서로 다른 클래스의 Pool을 교체하는 테스트로 동일 Actor 재사용을 검증할 수 없음.
11. 메모리와 성능: 대기 수 상한, 사용 중 Actor 보존, 목표 기기 예산, 동일 작업량의 Spawn/Destroy 비교.

## 이전 답변에서 확인된 수준

- 중복 반환으로 같은 포인터가 대기 배열에 중복될 수 있고 발사 상태가 덮어써질 수 있다는 점은 이해했다.
- 이전 타격 기록은 새 발사의 피해를 차단할 수 있으며, 충돌 이벤트 발생과 피해 필터를 구분하는 연습이 필요하다.
- 남은 피해량은 중복 합산보다 오래된 override 값 사용 문제일 수 있음을 설명 후 이해했다.
- 재사용 여부는 포인터로 확인할 수 있지만 피해 상태 초기화나 Timer 정리까지 증명하지는 못한다는 점을 보완했다.
- GameInstanceSubsystem의 생존과 참조된 World Actor의 생존을 혼동했으나 설명 후 구분했다.
- Destroy 호출과 즉시 메모리 해제·포인터 null화를 혼동했다.
- 숨기기만 한 Actor도 충돌 가능하다는 점을 이해했다.
- 메모리 예산을 초과하면 Pool 크기를 줄이거나 다른 방식과 비교해야 한다고 답했다.
