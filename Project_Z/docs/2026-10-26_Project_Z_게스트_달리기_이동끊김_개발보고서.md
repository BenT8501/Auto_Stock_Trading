# Project_Z 게스트 달리기 및 이동 끊김 버그 수정 개발 보고서

- 작성일: 2026-10-26
- 대상 프로젝트: Project_Z
- 대상 모드: FPS 멀티플레이
- 대상 클래스: `AZCharacter_FPS`
- 빌드 구성: `Project_ZEditor / Win64 / Development`
- 현재 상태: 코드 수정 및 전체 빌드 완료, 멀티플레이 PIE 최종 검증 대기

## 1. 작업 개요

멀티플레이 PIE 환경에서 게스트 플레이어에게 다음 문제가 발생했다.

1. 게스트가 LeftShift를 눌러도 달리기 속도가 정상적으로 적용되지 않음
2. 게스트가 이동할 때 바닥이나 턱에 반복적으로 걸리는 것처럼 위치가 끊겨 보임

두 현상을 별개 충돌 문제로 가정하지 않고 네트워크 이동 처리부터 점검했다. 확인 결과, 게스트와 서버가 서로 다른 `MaxWalkSpeed`를 사용하면서 서버 위치 보정이 반복되는 구조가 발견됐다.

## 2. 기존 구현 분석

기존 FPS 달리기 처리는 다음과 같았다.

- LeftShift 시작 시 로컬 `bIsRunning = true`
- LeftShift 취소 시 로컬 `bIsRunning = false`
- 이동 입력이 발생하는 매 프레임 `Move()`에서 `MaxWalkSpeed`를 300 또는 600으로 변경
- 달리기 상태와 이동 속도를 서버에 알리는 RPC 없음

호스트는 로컬 플레이어이면서 서버 권한도 가지므로 해당 방식이 우연히 정상 동작했다. 반면 게스트는 자신의 로컬 캐릭터에서만 속도를 600으로 변경했고, 서버의 같은 캐릭터는 계속 300을 사용했다.

## 3. 근본 원인

### 3.1 게스트 달리기 실패

게스트가 달리기를 시작하면 클라이언트 예측 이동은 600 속도를 기준으로 계산하지만 서버는 300을 기준으로 이동을 검증했다.

```text
게스트 입력
  → 게스트 MaxWalkSpeed = 600
  → 서버 MaxWalkSpeed = 300 유지
  → 서버가 게스트 이동 거리를 과도하다고 판단
  → 서버 위치로 보정
```

따라서 입력 자체는 들어왔지만 서버 권한 상태가 갱신되지 않아 실제 네트워크 게임에서는 달리기가 유지되지 않았다.

### 3.2 바닥에 걸리는 듯한 이동

게스트의 예상 위치와 서버 권한 위치가 계속 달라지면서 CharacterMovement의 서버 보정이 반복됐다. 화면에서는 이 보정이 짧은 후퇴, 떨림 또는 바닥 턱에 걸리는 것처럼 보일 수 있다.

현재 증거로는 바닥 메시 충돌보다 이동 속도 불일치가 두 증상을 함께 설명하는 우선 원인이다. 실제 바닥 충돌 문제인지 여부는 이번 수정 후 PIE 재검증으로 분리한다.

### 3.3 Shift 해제 이벤트 누락 가능성

기존 코드는 달리기 종료를 `ETriggerEvent::Canceled`에만 연결했다. 일반적인 버튼 해제는 Input Action 설정에 따라 `Completed`로 전달될 수 있으므로 Shift를 놓아도 달리기 상태가 종료되지 않을 가능성이 있었다.

## 4. 수정 내용

### 4.1 서버 달리기 RPC 추가

`AZCharacter_FPS`에 다음 RPC를 추가했다.

```cpp
UFUNCTION(Server, Reliable)
void ServerSetRunning(bool bRunning);
```

게스트가 달리기 시작 또는 종료 입력을 수행하면 로컬 상태를 즉시 변경해 입력 반응성을 유지하고, 동시에 서버 RPC를 호출해 서버 권한 캐릭터의 이동 속도도 동일하게 변경한다.

### 4.2 상태 적용 함수 통합

달리기 상태와 실제 속도 변경을 `ApplyRunningState()`로 통합했다.

```cpp
void AZCharacter_FPS::ApplyRunningState(bool bRunning)
{
    bIsRunning = bRunning;
    if (UCharacterMovementComponent* MovementComponent = GetCharacterMovement())
    {
        MovementComponent->MaxWalkSpeed = bIsRunning ? SprintSpeed : WalkSpeed;
    }
}
```

클라이언트와 서버가 같은 함수를 사용하므로 상태별 속도 계산이 분리되지 않는다.

### 4.3 이동 입력 함수 단순화

기존 `Move()` 함수에서 매 프레임 `MaxWalkSpeed`를 덮어쓰던 코드를 제거했다. 속도는 달리기 상태가 변경되는 시점에만 갱신한다.

이 변경으로 이동 입력 처리와 상태 변경 책임을 분리했다.

### 4.4 입력 종료 처리 보완

LeftShift 해제 처리를 다음 두 이벤트에 모두 연결했다.

```cpp
ETriggerEvent::Completed
ETriggerEvent::Canceled
```

정상적인 버튼 해제와 입력 취소 상황 모두 `StopRun()`으로 처리된다.

### 4.5 속도 설정값 프로퍼티화

다음 속도를 Blueprint Class Defaults에서 확인하거나 조정할 수 있도록 프로퍼티로 분리했다.

| 항목 | 기본값 |
|---|---:|
| `WalkSpeed` | 300 cm/s |
| `SprintSpeed` | 600 cm/s |

캐릭터 초기화가 끝난 뒤 `ApplyRunningState(false)`를 호출해 호스트와 게스트 모두 동일한 기본 걷기 속도로 시작한다.

## 6. 수정 후 처리 흐름

### 게스트 달리기 시작

```text
LeftShift Started
  → 게스트 ApplyRunningState(true)
  → 게스트 MaxWalkSpeed = 600
  → ServerSetRunning(true)
  → 서버 ApplyRunningState(true)
  → 서버 MaxWalkSpeed = 600
```

### 게스트 달리기 종료

```text
LeftShift Completed 또는 Canceled
  → 게스트 ApplyRunningState(false)
  → 게스트 MaxWalkSpeed = 300
  → ServerSetRunning(false)
  → 서버 ApplyRunningState(false)
  → 서버 MaxWalkSpeed = 300
```

호스트는 이미 서버 권한을 가지므로 별도 RPC 없이 같은 상태 적용 함수를 실행한다.

## 9. 완료 판정 기준

다음 조건을 모두 만족하면 두 버그를 완료 처리한다.

- 게스트가 LeftShift 입력 시 호스트와 동일한 체감 속도로 달린다.
- Shift를 놓으면 즉시 걷기 속도로 복귀한다.
- 게스트 이동 중 주기적인 후퇴나 떨림이 재현되지 않는다.
- 호스트 화면에서 관찰한 게스트 이동도 끊기지 않는다.
- 일반 이동과 실제 장애물 충돌이 정상적으로 구분된다.

## 10. 위험 요소 및 후속 판단

### 현재 구현의 적합 범위

이번 Reliable RPC 방식은 직무 과제와 소규모 멀티플레이 검증 수준에서는 충분히 실현 가능하다. 달리기 시작과 종료 시에만 RPC가 발생하므로 호출량도 낮다.

### 남아 있는 한계

경쟁형 FPS의 상용 이동 시스템에서는 달리기 상태를 CharacterMovement의 SavedMove 및 압축 플래그에 포함하는 방식이 더 정확하다. 해당 방식은 클라이언트 예측과 서버 재시뮬레이션에 달리기 상태가 직접 포함되지만 구현 범위가 커진다.

현재 과제 단계에서 이를 추가하는 것은 과도하다. 먼저 RPC 방식으로 실제 네트워크 보정 문제가 해소되는지 검증하는 것이 타당하다.

### 이동 끊김이 남는 경우

이번 수정 이후에도 동일 증상이 재현되면 다음 항목을 별도 조사한다.

1. 캐릭터 Capsule 크기와 바닥 침투 여부
2. `MaxStepHeight` 및 `WalkableFloorAngle`
3. 바닥 Static Mesh의 단순/복합 Collision 설정
4. 이동 중 접촉하는 WorldDynamic 오브젝트
5. 패킷 지연 및 손실 환경의 CharacterMovement 보정 빈도

바닥 Collision이나 StepHeight는 현재 원인을 검증하기 전에 임의로 변경하지 않았다. 잘못 변경하면 정상적인 장애물 통과와 계단 판정에 회귀 문제가 생길 수 있기 때문이다.
