# Project_Z 모의 면접 1회차 정리

- 진행일: 2026-09-11
- 기준: `Project_Z_Verification_Mock_Interview.md`
- 상태: 1회차 종료. 다음 회차는 아래 복습 항목부터 재검증한다.
- 이번 면접에서는 실제 C++ 소스, Blueprint 그래프, 로그 및 실행 결과를 직접 확인하지 않았다. 구현 관련 설명은 가이드와 응답자의 진술에 근거한다.

| 영역 | 점수 |
|---|---:|
| 프로젝트 소유 이해 | 12/20 |
| 호출 흐름 이해 | 11/20 |
| Unreal Framework 이해 | 7/15 |

| 데이터 설계 | 5/10 |

## 2. 확인된 강점과 진술

- 입력 바인딩에서 Ability, Character의 발사 처리로 이어지는 주요 흐름을 설명했다.
- Range, 투사체 이동 속도, 피해 데이터의 적용 목적을 설명했다.
- Wave 및 Monster Variant 데이터 로딩과 적 생성 흐름을 구체적으로 설명했다.
- 재장전 Montage와 완료 Notify를 연결한 목적을 설명했다.
- 공유 DataAsset을 수정하면 다른 참조자도 영향을 받는다는 점을 이해했다.
- 모르는 범위와 GAS에서 도움받은 사실을 인정했다. 성능을 측정하지 않았다는 점도 명확히 했다.
- GameMode, PlayerController, Character를 직접 설계·작성했다고 진술했다. 실제 작성 범위는 코드와 작업 기록으로 추가 확인이 필요하다.
- 헤드샷을 HUD 수치와 로그로 검증했으며, 로그에서 판정 여부·피해량·적용 후 HP를 확인했다고 진술했다. 실제 수치와 로그는 확인하지 않았다.

## 3. 핵심 복습 사항

### 클래스 책임과 입력

- 가이드 기준 PlayerController는 HUD·게임 흐름 UI·입력 모드·커서를 관리한다. Character는 데이터만 보유하는 객체가 아니라 이동·조준·공격 입력과 실행 로직도 담당한다.
- 입력 흐름: `IA_Ability_Primary`의 Started → `OnAbilityInputPressed()` → 등록된 Spec의 `InputID` 비교 → `TryActivateAbility(Handle)` → `ActivateAbility()` → Avatar를 Character로 Cast → `ActivatePrimaryWeapon()`.
- Ability 등록은 `GiveAbility()`가 담당한다. 등록, 입력 ID 매칭, 활성화 성공은 서로 다른 단계다.
- `TryActivateAbility()` 호출만으로 활성화가 보장되지는 않는다. 활성화 진입과 이후 발사 실패를 나눠 디버깅한다.

### 투사체와 Pool

가이드의 발사 경로 기준:

| 8개 발사 설정에서 획득 결과 | 실제 발사 수 | 함수 반환 | 탄약 차감 |
|---|---:|---|---:|
| 8개 성공 | 8 | true | 1 |
| 3개 성공 | 3 | true | 1 |
| 전부 실패 | 0 | false | 0 |

- 풀에 대기 Actor가 없는 것과 최종 획득 실패는 다르다. 발사 함수가 실패분을 별도 생성해 보충한다고 가정하지 않는다.
- `RuntimeHitActors`는 한 발에서 중복 피해를 막는 기록이다. 새 발사 전에 비우지 않으면 이전에 맞힌 적에게 피해를 주지 못할 수 있다.
- 중복 반환은 같은 Actor 포인터를 대기 배열에 중복 저장할 수 있다. 두 번째 획득·설정이 첫 발의 위치·방향·피해 등을 덮어쓴다.
- 제안된 방어: `InUseActors`에서 실제 제거에 성공했을 때만 `AvailableActors`에 추가한다.
- World 소속 Actor의 풀 수명은 `UWorldSubsystem`으로 맞춘다. World Settings와 구분한다.
- Pool은 생성·파괴 및 GC 부담을 줄이려는 방식이다. 대기 Actor를 유지하므로 메모리 사용량은 늘 수 있다.

### Owner와 헤드샷

- `this`: 투사체 자신. `GetOwner()`: 이 예시에서 발사자. `OtherActor`: 충돌한 객체.
- `OtherActor == GetOwner()`는 같은 객체인지 비교한다. 적인지 벽인지 판단하는 조건이 아니다.
- `ComponentTags`에 넣은 태그는 해당 컴포넌트에서 읽는다. 맞은 부위를 구분하려면 `OtherComp`가 중요하다.
- 응답자는 머리 Collision의 `HeadHitbox` 태그로 헤드샷을 구분했다고 진술했지만 실제 검사 위치는 기억하지 못했다.
- 가이드는 Bone 이름과 높이 비율 기반 보조 판정을 기록한다. 태그 방식과 실제로 어떻게 연결되는지는 코드·Blueprint 확인 전까지 미확인으로 남긴다.

### GAS와 HP: 현재 구현과 수정 가정 구분

- `BaseDamage`는 피해 계산의 기본 수치다. 직접 피해 경로라는 뜻이 아니다.
- 가이드에서 말하는 직접 피해는 `CurrentHP`를 직접 감소시키는 기존 경로다.
- GAS 피해는 최종 수치를 `Data.Damage` 키의 SetByCaller로 EffectSpec에 전달하고, GameplayEffect를 통해 AttributeSet에서 처리하는 경로다.
- `Damage`는 이번 피해 처리에 소비하는 임시 Meta Attribute, `HP`는 유지할 체력 상태다. 피해 처리 후 Damage를 0으로 초기화한다.

**가이드에 기록된 현재 구현:**

| 단계 | CurrentHP | AttributeSet::HP |
|---|---:|---:|
| 초기 | 30 | 30 |
| 직접 피해 20 | 10 | 30 |
| GAS 피해 5 | 10 | 25 |
| AttributeSet에서 CurrentHP로 동기화 | 25 | 25 |

직접 피해가 처음부터 무시되는 것이 아니라, 이후 복사에서 그 결과가 유실된다.

**제안한 수정 가정:** AttributeSet::HP를 유일한 원천으로 두고 기존 직접 피해도 공통 GameplayEffect 경로로 전환한다. 두 피해를 어느 순서로 적용해도 최종 HP는 5다. 실제 코드 수정은 수행하지 않았다.

면접 중 현재 구현과 수정 가정을 오가며 질문해 혼동이 발생했다. 다음 회차에는 각 문제의 전제를 먼저 명시하고, 해당 구간의 점수만으로 이해도를 확정하지 않는다.

### 스테이지 상태

- 생성 성공 시에만 `AliveEnemyCount`를 증가시킨다. 실패한 Actor는 사망 통지를 보낼 수 없어 잘못 증가한 수가 남는다.
- 생성 시도 종료 후 전체 실패 처리도 필요하다. Tick에서 0일 때마다 무제한 생성하면 정상 클리어와 실패를 혼동할 수 있다.
- 면접에서 제안한 `SpawnSuccessCount`는 기존 구현으로 확인한 변수가 아니라 수정 설계 예시다. 이번 실행의 누적 생성 성공 수이므로 GameMode 런타임 상태에 둔다.
- 7명 생성 후 2명 사망: SpawnSuccessCount는 7, AliveEnemyCount는 5.
- DataTable의 생성 목표와 실제 생성 성공 수는 구분한다.

### 데이터·UI·재장전·성능

- DataAsset: 무기 하나의 리소스와 수치를 독립 콘텐츠 단위로 묶어 참조하기 편하다.
- DataTable: 동일 구조의 여러 Wave·Variant를 행으로 비교·편집하기 편하다. 기본 정보 대 직접 적용 정보의 구분이 아니다.
- DataAsset과 DataTable 모두 공유 정의를 담을 수 있다. 캐릭터별 보너스는 런타임 상태로 분리한다.
- HUD 이벤트 갱신은 발사 외에 재장전·장비 변경 등 모든 관련 변경 경로를 포함해야 한다.
- 완료 Notify 전에 재장전이 취소되면 탄약은 유지하고 재장전 상태를 해제한다. 종료·중단 경로를 별도로 연결한다.
- 성능 비교는 동일 조건의 Spawn/Destroy와 Pool을 대상으로 Game Thread 시간, 프레임 지연, GC, 메모리를 확인한다. 메모리 비용과 목표 기기의 예산도 함께 고려한다.

## 4. 합의된 수정 후보와 검증 기준

실제 수정은 아직 수행하지 않았다. 응답자는 게임 진행을 막는 카운트 오류를 최우선으로 선택했다.

| 우선순위 | 작업 | 검증 |
|---|---|---|
| 1 | 생성 성공과 생존 카운트 연결, 전체 생성 실패 정책 | 일부·전체 실패를 유도해 카운트가 실제 생성 수와 일치하고 실패 시 정해진 복구·오류 처리가 실행되는지 확인 |
| 2 | 피해 경로와 HP 원천 일원화 | HP 30에 피해 20·5를 양쪽 순서로 적용해 최종 5인지 확인 |
| 3 | Pool 중복 반환 방어 | 같은 Actor를 두 번 반환해 대기 목록에 한 번만 존재하고 연속 획득이 사용 중 Actor를 중복 지급하지 않는지 확인 |

## 5. 다음 회차 진행 방법

- 한 번에 질문 하나, 정답 선공개 없이 진행한다.
- 최초 답변과 설명 후 확인 답변을 구분한다. 익숙하지 않은 용어는 정의한 뒤 검증한다.
- 먼저 현재 구현과 수정 가정, 직접 피해와 BaseDamage의 차이를 짧게 확인한다.
- 숫자 계산만 반복하기보다 객체 책임·값 변경·실패 조건·디버깅 지점을 연결해서 묻는다.
- 권장 순서: 클래스 책임 → 입력/Ability → 발사 성공과 탄약 → Owner/충돌 → GAS와 HP → Stage 카운트 → Pool → 수정·검증 계획.
- 가능하면 실제 소스와 Blueprint를 열고 HeadHitbox 검사 위치, HP 변경 경로, Spawn 반환값, Pool 반환 조건을 확인한다. 자료가 없으면 가이드 기반 평가라는 한계를 유지한다.
