## 1. 확정한 목표

- 접속할 때 A팀 또는 B팀을 한 번 선택한다.
- 서버에서 승인한 뒤에는 같은 접속 동안 팀을 바꿀 수 없다.
- 선택 전에는 전투용 FPS Pawn을 생성하지 않는다.
- 서버가 팀을 저장하고 해당 팀 위치에 Pawn을 생성한다.
- 소유 클라이언트에서 팀 정보와 Pawn을 확인한 뒤 선택 UI를 닫고 전투 HUD를 표시한다.
- 사망·리스폰 시 기존 PlayerState의 팀을 유지하며 다시 선택하지 않는다.
- 퇴장 후 새로 접속하면 새 PlayerState의 None 상태에서 다시 선택한다. 재접속 팀 복원은 이번 범위가 아니다.

이번 요청으로 기존 '접속 즉시 자동 배정' 흐름을 '접속 시 사용자 선택'으로 변경한다. 기존 자동 배정 구현 문서는 과거 구현 기록으로 보존한다.

아직 확정하지 않은 정책은 임의로 넣지 않는다.

| 정책 | 이번 최소 구현 |
|---|---|
| 팀별 정원 3명 제한 | 미확정. 강제하지 않음 |
| 인원이 많은 팀 선택 금지 | 미확정. 강제하지 않음 |
| 최대 6인 접속 제한 | 기존 후속 일정에서 별도 구현 |
| 자동 선택 버튼 | 이번 UI에는 넣지 않음 |
| 플레이 중 팀 변경 | 허용하지 않음 |
| 아군 피해 차단 | 이 가이드 범위 밖 |
| 선택 화면 캐릭터 미리보기 | 구현하지 않음 |

따라서 최소 구현에서는 두 명이 같은 팀을 선택할 수도 있다. 서버 검사 함수를 한 곳에 두어 정원·균형 규칙이 확정되면 그곳에 추가한다.

## 2. 최종 실행 흐름

```text
접속
 → 서버 PostLogin: PlayerState 타입 확인, 자동 배정하지 않음
 → 최초 스폰 진입: 팀 None이면 대기
 → 소유 클라이언트 Controller: 팀 선택 UI 표시
 → 사용자가 A/B 버튼 클릭
 → Controller의 Server RPC로 팀 enum 전달
 → GameMode에서 유효한 요청인지 검사
     ├─ 거절: 소유 클라이언트에 사유 전달, 다시 선택 가능
     └─ 승인: PlayerState에 팀 저장
          → 팀별 PlayerStart에서 RestartPlayer
          ├─ 실패: 팀은 유지, 같은 팀 스폰 재시도 제공
          └─ 성공: Pawn 생성·소유 및 네트워크 전달
 → 클라이언트에서 팀 배정과 FPS Pawn 소유 확인
 → 선택 UI 제거, 게임 입력 복구, 기존 HUD 생성
 → 사망 시 기존 팀으로 리스폰
```

팀 값·RPC 응답·Pawn이 클라이언트에 도착하는 순서를 가정하지 않는다. '서버가 승인함'과 '로컬 전투 화면을 사용할 준비가 됨'을 구분한다.

### 3.1 필수 선행 함수 확인 — 없으면 먼저 추가

위 표의 '현재 상태'는 문서 작성자가 확인한 작업 공간 기준이다. 사용자가 편집 중인 코드에도 반드시 같은 함수가 있다고 가정하면 안 된다. **아래 사용자 정의 함수는 언리얼 기본 기능이 아니다.** 가이드 본문에서 호출하기 전에 해당 클래스의 선언과 구현을 확인한다.

| 사용 항목 | 소속/역할 | 없을 때 할 작업 |
|---|---|---|
| GetPlayerTeam() | AProject_Z_MultiPlayerState. 저장된 팀 반환 | 아래 헤더 인라인 함수 추가 |
| HasAssignedTeam() | AProject_Z_MultiPlayerState. 팀 선택 완료 여부 반환 | 아래 헤더 인라인 함수 추가 |
| SetPlayerTeam() | AProject_Z_MultiPlayerState. 서버에서 팀 저장 및 변경 통지 | 기존 팀 데이터 구현의 선언·CPP 본문 확인. 이름만 선언하면 안 됨 |
| PlayerTeam | AProject_Z_MultiPlayerState. 복제되는 팀 원본 값 | 기존 저장 변수와 ReplicatedUsing/DOREPLIFETIME 설정 확인. 동일 역할 변수 중복 생성 금지 |
| OnRep_PlayerTeam / OnPlayerTeamChanged | AProject_Z_MultiPlayerState. 팀 변경 통지 | 기존 팀 복제 구현 확인 |

**[전체 함수 예시 제공 — 없을 때 추가] GetPlayerTeam / HasAssignedTeam**

수정할 파일은 `Public/PlayerStates/Project_Z_MultiPlayerState.h`다. `AProject_Z_MultiPlayerState` 클래스의 public 영역에 다음을 추가한다. 이미 같은 선언이나 구현이 있으면 중복 추가하지 않는다.

```cpp
public:
    UFUNCTION(BlueprintPure, Category = "Z|Team")
    EZPlayerTeam GetPlayerTeam() const
    {
        return PlayerTeam;
    }

    UFUNCTION(BlueprintPure, Category = "Z|Team")
    bool HasAssignedTeam() const
    {
        return PlayerTeam != EZPlayerTeam::None;
    }
```

이 예시는 헤더 안에 함수 본문까지 작성하는 방식이므로 CPP에 같은 본문을 추가하지 않는다. 기존에 선언만 있다면 해당 선언을 위처럼 본문이 있는 형태로 바꾸거나, 선언은 유지하고 CPP에 본문을 작성하는 방식 중 하나만 선택한다.

필요 조건은 `Multiplayer/ZTeamTypes.h` include와 기존 `EZPlayerTeam PlayerTeam` 멤버다. 팀 저장 멤버의 이름이 다르면 기존 멤버에 맞춰 함수 본문을 작성한다. 함수 때문에 별도의 팀 변수를 추가하지 않는다.

`HasAssignedTeam()`은 **PlayerTeam이 None이 아닌지 확인하는 편의 함수**다. None이면 false, 이미 팀이 있으면 true를 반환한다. 스폰 여부나 서버 권한을 검사하는 함수는 아니다. 팀 값의 유효성은 TrySelectPlayerTeam에서 별도로 검사한다.

사용 예는 다음과 같다.

```cpp
// PS는 AProject_Z_MultiPlayerState*이며 앞에서 유효성을 검사한 상태.
if (PS->HasAssignedTeam())
{
    // 이미 선택한 팀이 있으므로 두 번째 선택 요청을 거절한다.
}
```

이 가이드에서 새로 만드는 TrySelectPlayerTeam과 달리, 위 두 조회 함수는 기존 팀 데이터 코드에 있다는 전제로 사용했던 의존 함수다. 사용자 코드에 없다면 **이 절에서 먼저 구현한 후** 5절 이후로 진행한다. SetPlayerTeam/PlayerTeam/복제 구현까지 없다면 단순 조회 함수 두 개만 추가해서 진행할 수 없으며, 기존 팀 데이터 구현을 먼저 맞춰야 한다.

### 3.2 팀 데이터 구현이 빠져 있을 때의 기준 코드

**[선행 준비 — 전체 예시 제공]** 아래는 기존 소스와 대조하기 위한 코드다. 기존 파일 전체를 덮어쓰라는 뜻이 아니다. 같은 클래스의 다른 기능은 유지하고 없는 선언/본문만 추가한다. 이미 존재하는 함수, enum, delegate, 복제 등록을 중복 작성하지 않는다.

`Public/Multiplayer/ZTeamTypes.h`에는 다음 팀 타입이 필요하다.

```cpp
#pragma once
#include "CoreMinimal.h"
#include "ZTeamTypes.generated.h"

UENUM(BlueprintType)
enum class EZPlayerTeam : uint8
{
    None UMETA(DisplayName = "None"),
    TeamA UMETA(DisplayName = "Team A"),
    TeamB UMETA(DisplayName = "Team B")
};
```

`Public/PlayerStates/Project_Z_MultiPlayerState.h`의 팀 기능 기준이다. 3.1에서 조회 함수를 이미 추가했다면 그대로 유지하며 중복 추가하지 않는다.

```cpp
#pragma once
#include "CoreMinimal.h"
#include "GameFramework/PlayerState.h"
#include "Multiplayer/ZTeamTypes.h"
#include "Project_Z_MultiPlayerState.generated.h"

DECLARE_DYNAMIC_MULTICAST_DELEGATE_TwoParams(
    FZOnPlayerTeamChanged,
    EZPlayerTeam, PreviousTeam,
    EZPlayerTeam, NewTeam);

UCLASS()
class PROJECT_Z_API AProject_Z_MultiPlayerState : public APlayerState
{
    GENERATED_BODY()

public:
    virtual void GetLifetimeReplicatedProps(
        TArray<FLifetimeProperty>& OutLifetimeProps) const override;

    UFUNCTION(BlueprintPure, Category = "Z|Team")
    EZPlayerTeam GetPlayerTeam() const { return PlayerTeam; }

    UFUNCTION(BlueprintPure, Category = "Z|Team")
    bool HasAssignedTeam() const { return PlayerTeam != EZPlayerTeam::None; }

    UPROPERTY(BlueprintAssignable, Category = "Z|Team")
    FZOnPlayerTeamChanged OnPlayerTeamChanged;

private:
    friend class AProject_Z_MultiGameMode;
    void SetPlayerTeam(EZPlayerTeam NewTeam);

    UFUNCTION()
    void OnRep_PlayerTeam(EZPlayerTeam PreviousTeam);

    UPROPERTY(VisibleAnywhere, BlueprintReadOnly,
        ReplicatedUsing = OnRep_PlayerTeam,
        Category = "Z|Team", meta = (AllowPrivateAccess = "true"))
    EZPlayerTeam PlayerTeam = EZPlayerTeam::None;
};
```

`Private/PlayerStates/Project_Z_MultiPlayerState.cpp`에 필요한 본문이다. 기존 GetLifetimeReplicatedProps가 있으면 Super 호출을 중복하지 않고 PlayerTeam 등록만 병합한다. 기존 OnRep의 로그나 추가 동작은 유지한다.

```cpp
#include "PlayerStates/Project_Z_MultiPlayerState.h"
#include "Net/UnrealNetwork.h"

void AProject_Z_MultiPlayerState::GetLifetimeReplicatedProps(
    TArray<FLifetimeProperty>& OutLifetimeProps) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);
    DOREPLIFETIME(AProject_Z_MultiPlayerState, PlayerTeam);
}

void AProject_Z_MultiPlayerState::SetPlayerTeam(EZPlayerTeam NewTeam)
{
    if (!HasAuthority() || PlayerTeam == NewTeam)
    {
        return;
    }
    const EZPlayerTeam PreviousTeam = PlayerTeam;
    PlayerTeam = NewTeam;
    OnPlayerTeamChanged.Broadcast(PreviousTeam, PlayerTeam);
    ForceNetUpdate();
}

void AProject_Z_MultiPlayerState::OnRep_PlayerTeam(EZPlayerTeam PreviousTeam)
{
    OnPlayerTeamChanged.Broadcast(PreviousTeam, PlayerTeam);
}
```

OnPlayerTeamChanged는 위에서 선언한 사용자 정의 delegate이며 Broadcast는 delegate의 호출 기능이다. OnRep_PlayerTeam은 PlayerTeam 복제 수신 시 호출되도록 연결한 사용자 정의 함수다. SetPlayerTeam은 서버에서 값 변경과 통지를 수행한다. 승인 검증은 7절의 GameMode가 담당한다.

GameMode 생성자의 `PlayerStateClass = AProject_Z_MultiPlayerState::StaticClass();` 설정과 실제 맵의 GameMode BP에서 사용하는 PlayerState Class도 확인한다. 함수가 있어도 실제 생성된 클래스가 다르면 GetPlayerState의 타입 변환이 실패한다.

## 5. 1단계 — 자동 배정 중단과 최초 스폰 대기

**선행 조건:** 3절의 HasAssignedTeam/PlayerState 구현과 4.1의 GameMode 선언을 먼저 준비한다. 이 절만 적용하고 팀 선택 기능 전체를 테스트하는 단계는 아니다.

### 5.1 PostLogin 수정

**[기존 코드 수정]** 아래는 추가할 코드가 아니라 기존 함수에서 제거할 호출이다.

`Project_Z_MultiGameMode.cpp`의 기존 `PostLogin()`에서 아래 호출만 제거한다.

```cpp
AssignBalancedTeam(NewPlayerState);
```

`Super::PostLogin(NewPlayer)`와 PlayerState 유효성 검사는 유지한다. 실패 로그의 문구는 '팀 배정 실패' 대신 '팀 선택 초기화 실패'로 바꿔도 된다. 이 단계에서 팀을 None으로 매번 대입하지 않는다. 신규 PlayerState의 기존 기본값이 이미 None이다.

### 5.2 자동 배정만 제거하면 안 되는 이유

기본 스폰 경로는 팀 선택을 기다린다는 규칙을 모른다. PostLogin 수정만으로 Pawn 생성을 막았다고 판단하면 안 된다.

GameMode 헤더에 추가할 선언:

```cpp

    virtual void HandleStartingNewPlayer_Implementation(
        APlayerController* NewPlayer) override;

    virtual void RestartPlayer(AController* NewPlayer) override;
```

최초 입장 대기 구현 예시:

**[전체 함수 예시 제공]** HandleStartingNewPlayer와 RestartPlayer의 본문은 아래에 있다.

```cpp
void AProject_Z_MultiGameMode::HandleStartingNewPlayer_Implementation(
    APlayerController* NewPlayer)
{
    const AProject_Z_MultiPlayerState* PS = IsValid(NewPlayer)
        ? NewPlayer->GetPlayerState<AProject_Z_MultiPlayerState>()
        : nullptr;

    if (!IsValid(PS) || !PS->HasAssignedTeam())
    {
        return;
    }

    Super::HandleStartingNewPlayer_Implementation(NewPlayer);
}
```

최초 스폰뿐 아니라 다른 경로의 재스폰도 팀 미선택 상태에서는 실행되지 않도록 공통 진입점에 검사를 둔다.

```cpp
void AProject_Z_MultiGameMode::RestartPlayer(AController* NewPlayer)
{
    const AProject_Z_MultiPlayerState* PS = IsValid(NewPlayer)
        ? NewPlayer->GetPlayerState<AProject_Z_MultiPlayerState>()
        : nullptr;

    if (!IsValid(PS) || !PS->HasAssignedTeam() || NewPlayer->GetPawn())
    {
        return;
    }

    // 아래 2단계의 팀별 시작점 선택 구현과 함께 적용한다.
    AActor* StartSpot = FindPlayerStart(NewPlayer);
    if (!IsValid(StartSpot))
    {
        UE_LOG(LogTemp, Warning, TEXT("[TeamSpawn] No available start for %s"),
            *GetNameSafe(NewPlayer));
        return;
    }

    RestartPlayerAtPlayerStart(NewPlayer, StartSpot);
}
```

두 검사는 초기 입장과 다른 경로의 RestartPlayer 호출을 각각 제한한다. 기존 리스폰 코드는 UnPossess 후 RestartPlayer를 호출하므로 기존 팀이 있으면 통과한다.

여기서는 시작점을 직접 확인한 뒤 RestartPlayerAtPlayerStart를 호출한다. 기본 RestartPlayer에는 새 시작점을 못 찾으면 Controller에 저장된 이전 StartSpot을 사용하는 경로가 있기 때문이다. 사용 가능한 팀 시작점이 없을 때는 실패로 남기려는 이번 정책에 맞춰 그 우회를 차단한다. 따라서 1단계의 RestartPlayer와 2단계의 시작점 선택 함수를 함께 적용한다.

맵에 미리 배치한 FPS 캐릭터의 Auto Possess Player, BP의 직접 SpawnActor/Possess, RestartPlayerAtTransform 등의 별도 경로가 있다면 이번 흐름을 우회하지 않는지 확인한다. 기본 엔진 경로를 제한했다고 임의의 BP 생성까지 차단되는 것은 아니다.

**완료 확인:** 접속해도 전투 Pawn이 생성되지 않고 PlayerState 팀은 None이다. 아직 선택 UI를 만들기 전이므로 화면이 대기 상태인 것은 정상이다.

### 6.3 두 함수의 차이와 서버 실행 여부

두 함수는 서로 다른 역할을 가진다.

| 함수 | 역할 | 이번 구현 |
|---|---|---|
| FindPlayerStart | 이번 스폰에 사용할 시작점을 구하는 진입점. 기본 구현은 이름으로 지정한 지점이나 저장된 지점을 사용하거나 ChoosePlayerStart에 선택을 맡긴다. | 매번 ChoosePlayerStart를 호출한다. |
| ChoosePlayerStart | 새로운 시작점이 필요할 때 후보 중 하나를 선택한다. | 해당 팀의 PlayerStart 중 캐릭터가 들어갈 수 있는 지점을 선택한다. |

**네트워크 플레이에서는 서버의 GameMode에서 실행된다. 다만 Server RPC 함수는 아니다.** GameMode는 서버에만 존재하며, 클라이언트가 이 함수를 호출해서 서버에 요청하는 구조가 아니다. 리슨 서버의 호스트도 서버 GameMode를 사용하고, 단독 실행에서는 로컬 GameMode가 실행한다.

클라이언트의 팀 선택 요청은 소유한 PlayerController의 Server RPC로 전달한다. 그 뒤 서버가 팀을 승인하고 아래 스폰 경로를 실행한다.

```text
클라이언트: 팀 버튼 클릭
  → PlayerController의 ServerRequestTeamSelection (Server RPC)
서버: 팀 승인 / PlayerState 팀 기록
  → RestartPlayer
  → FindPlayerStart
  → ChoosePlayerStart
  → 시작점이 유효하면 RestartPlayerAtPlayerStart
  → Pawn 생성 및 Possess
```

`_Implementation`이라는 이름만 보고 RPC라고 판단하면 안 된다. 이 두 함수는 엔진에 BlueprintNativeEvent로 선언되어 있어서 C++ 기본 동작을 `_Implementation`에서 구현한다. Server RPC도 같은 접미사를 사용하지만, 서버 RPC인지는 원래 선언의 `UFUNCTION(Server, ...)` 지정 여부로 구분한다.

따라서 기존 엔진 함수에 `UFUNCTION(Server, Reliable)`을 추가하지 않는다. 앞의 override 선언만 작성한다. 호출할 때는 `ChoosePlayerStart(Player)`처럼 이벤트 함수를 호출하고, C++ 구현할 때만 `_Implementation`을 붙인다. BP GameMode에 같은 이벤트를 따로 override했다면 그 BP 로직이 C++ 구현을 대체할 수 있으므로 함께 확인한다.

### 6.4 ChoosePlayerStart 실제 구현 예시

```cpp
AActor* AProject_Z_MultiGameMode::ChoosePlayerStart_Implementation(
    AController* Player)
{
    UWorld* World = GetWorld();
    if (!HasAuthority() || !IsValid(World) || !IsValid(Player))
    {
        return nullptr;
    }

    const AProject_Z_MultiPlayerState* PS =
        Player->GetPlayerState<AProject_Z_MultiPlayerState>();
    if (!IsValid(PS))
    {
        return nullptr;
    }

    FName TeamTag = NAME_None;
    switch (PS->GetPlayerTeam())
    {
    case EZPlayerTeam::TeamA:
        TeamTag = TEXT("TeamA");
        break;
    case EZPlayerTeam::TeamB:
        TeamTag = TEXT("TeamB");
        break;
    default:
        return nullptr;
    }

    // 이 Controller에게 실제로 생성할 Pawn 클래스의 기본 캡슐을 사용한다.
    UClass* PawnClass = GetDefaultPawnClassForController(Player);
    const ACharacter* DefaultCharacter = PawnClass
        ? Cast<ACharacter>(PawnClass->GetDefaultObject())
        : nullptr;
    const UCapsuleComponent* Capsule = DefaultCharacter
        ? DefaultCharacter->GetCapsuleComponent()
        : nullptr;
    if (!IsValid(Capsule))
    {
        UE_LOG(LogTemp, Warning,
            TEXT("[TeamSpawn] Character capsule missing. PawnClass=%s"),
            *GetNameSafe(PawnClass));
        return nullptr;
    }

    const FCollisionShape Shape = FCollisionShape::MakeCapsule(
        Capsule->GetScaledCapsuleRadius(),
        Capsule->GetScaledCapsuleHalfHeight());
    const FCollisionResponseParams Responses(
        Capsule->GetCollisionResponseToChannels());

    for (TActorIterator<APlayerStart> It(World); It; ++It)
    {
        APlayerStart* Start = *It;
        if (!IsValid(Start) || Start->PlayerStartTag != TeamTag)
        {
            continue;
        }

        FCollisionQueryParams QueryParams;
        QueryParams.AddIgnoredActor(Start);

        const bool bBlocked = World->OverlapBlockingTestByChannel(
            Start->GetActorLocation(),
            Start->GetActorQuat(),
            Capsule->GetCollisionObjectType(),
            Shape,
            QueryParams,
            Responses);

        if (!bBlocked)
        {
            UE_LOG(LogTemp, Log,
                TEXT("[TeamSpawn] Player=%s Team=%s Start=%s"),
                *GetNameSafe(Player), *TeamTag.ToString(),
                *GetNameSafe(Start));
            return Start;
        }
    }

    UE_LOG(LogTemp, Warning,
        TEXT("[TeamSpawn] No free start. Player=%s Team=%s"),
        *GetNameSafe(Player), *TeamTag.ToString());
    return nullptr;
}
```

코드는 다음 순서로 읽으면 된다.

1. PlayerState의 팀을 확인하고 검색할 태그를 결정한다.
2. 생성할 캐릭터의 기본 캡슐 크기와 충돌 설정을 가져온다.
3. 같은 팀의 PlayerStart만 검사한다.
4. 해당 위치에서 캡슐이 벽이나 다른 Pawn에 막히면 다음 후보를 검사한다.
5. 사용 가능한 첫 후보를 반환하고, 없으면 nullptr로 실패를 알린다.

이 검사는 캡슐의 실제 충돌 응답을 따른다. 캐릭터끼리 Pawn 채널을 Ignore/Overlap하도록 설정했다면 서로를 막힌 위치로 판단하지 않는다. 현재 단계에서는 캐릭터 캡슐끼리 Block하는 설정을 전제로 확인한다. BeginPlay 등에서 캡슐 크기를 변경한다면 기본 객체의 크기와 달라지므로 해당 정책도 맞춰야 한다. PlayerStart는 똑바로 세워 배치한다.

현재는 사용 가능한 첫 후보를 선택한다. 무작위 선택이나 적과의 거리 기반 선택은 포함하지 않는다. 모든 팀 지점이 막혔을 때 다른 팀으로 스폰하지 않고, 이후 단계의 실패/재시도 흐름을 사용한다.

## 7. 3단계 — GameMode에 서버 선택 처리 추가

**선행 조건:** 3절의 SetPlayerTeam 및 friend 선언, 4.1의 TrySelectPlayerTeam 선언, 6절의 팀 시작점 설정이 필요하다.

외부 진입 함수는 예를 들어 다음으로 둔다.

```cpp
bool TrySelectPlayerTeam(
    APlayerController* Player,
    EZPlayerTeam RequestedTeam,
    FText& OutFailureReason);
```

이 함수의 성공은 **팀 선택 승인**이다. Pawn 생성 성공과 구분한다.

`TrySelectPlayerTeam`은 엔진에서 제공하는 함수가 아니다. 이번 기능을 위해 `AProject_Z_MultiGameMode`에 새로 작성하는 일반 C++ 함수다. 아래 검증 순서를 직접 코드로 옮기는 것이 이 단계의 작업이다. Controller에서 호출할 수 있도록 위 선언은 GameMode 헤더의 public 영역에 추가한다. override나 Server RPC 선언은 붙이지 않는다. 서버의 Controller RPC 구현에서 서버 GameMode를 가져와 호출한다.

반환값은 승인 여부이며, `OutFailureReason`은 실패 사유를 호출자에게 돌려주는 출력 인자다. 성공 시에는 비어 있다. 실제 Pawn 생성은 호출자가 승인 후 RestartPlayer로 진행한다.

서버 검증 순서:

1. 서버 권한인지 확인한다.
2. Controller와 그 MultiPlayerState가 유효한지 확인한다.
3. RequestedTeam이 정확히 TeamA 또는 TeamB인지 검사한다. None과 알 수 없는 enum 값을 거절한다.
4. 이미 팀이 있으면 변경 요청을 거절한다. 죽었거나 Pawn이 없더라도 팀 변경은 허용하지 않는다.
5. 예상치 못한 전투 Pawn이 이미 있으면 오류를 기록하고 자동으로 파괴하지 않는다.
6. 요청 팀에 해당하는 시작점이 구성되어 있는지 확인한다.
7. 추후 정원·균형 규칙은 이 지점에 추가한다. 현재는 미확정이므로 강제하지 않는다.
8. `PS->SetPlayerTeam(RequestedTeam)`으로 팀을 저장한다.
9. 성공을 반환한다.

### TrySelectPlayerTeam 구현 예시

**[전체 함수 예시 제공]**

`Project_Z_MultiGameMode.cpp`에 아래 함수를 추가한다. 기존 include와 중복되는 줄은 다시 추가하지 않는다.

```cpp
#include "GameFramework/PlayerController.h"
#include "GameFramework/PlayerStart.h"
#include "PlayerStates/Project_Z_MultiPlayerState.h"
#include "Multiplayer/ZTeamTypes.h"
#include "EngineUtils.h"
```

```cpp
bool AProject_Z_MultiGameMode::TrySelectPlayerTeam(
    APlayerController* Player,
    EZPlayerTeam RequestedTeam,
    FText& OutFailureReason)
{
    OutFailureReason = FText::GetEmpty();

    if (!HasAuthority())
    {
        OutFailureReason = FText::FromString(TEXT("팀 선택은 서버에서 처리합니다."));
        return false;
    }

    if (!IsValid(Player) || Player->GetWorld() != GetWorld())
    {
        OutFailureReason = FText::FromString(TEXT("플레이어 정보를 확인할 수 없습니다."));
        return false;
    }

    AProject_Z_MultiPlayerState* PS =
        Player->GetPlayerState<AProject_Z_MultiPlayerState>();
    if (!IsValid(PS))
    {
        OutFailureReason = FText::FromString(TEXT("PlayerState가 준비되지 않았습니다."));
        return false;
    }

    if (RequestedTeam != EZPlayerTeam::TeamA &&
        RequestedTeam != EZPlayerTeam::TeamB)
    {
        OutFailureReason = FText::FromString(TEXT("A팀 또는 B팀을 선택해 주세요."));
        return false;
    }

    if (PS->HasAssignedTeam())
    {
        OutFailureReason = FText::FromString(TEXT("이미 팀 선택이 완료되었습니다."));
        return false;
    }

    // 이번 흐름은 팀 선택 전 Pawn이 없는 상태를 전제로 한다.
    if (IsValid(Player->GetPawn()))
    {
        UE_LOG(LogTemp, Warning,
            TEXT("[TeamSelect] Unexpected pawn before selection. Player=%s Pawn=%s"),
            *GetNameSafe(Player), *GetNameSafe(Player->GetPawn()));
        OutFailureReason = FText::FromString(TEXT("입장 상태를 확인해야 합니다."));
        return false;
    }

    const FName TeamTag = RequestedTeam == EZPlayerTeam::TeamA
        ? FName(TEXT("TeamA"))
        : FName(TEXT("TeamB"));

    bool bHasTeamStart = false;
    for (TActorIterator<APlayerStart> It(GetWorld()); It; ++It)
    {
        if (IsValid(*It) && It->PlayerStartTag == TeamTag)
        {
            bHasTeamStart = true;
            break;
        }
    }

    if (!bHasTeamStart)
    {
        UE_LOG(LogTemp, Warning,
            TEXT("[TeamSelect] Missing PlayerStart. Team=%s"),
            *TeamTag.ToString());
        OutFailureReason = FText::FromString(TEXT("선택한 팀의 시작점이 설정되지 않았습니다."));
        return false;
    }

    // 팀 정원/균형 제한은 현재 확정하지 않았으므로 추가하지 않는다.
    PS->SetPlayerTeam(RequestedTeam);

    UE_LOG(LogTemp, Log,
        TEXT("[TeamSelect] Accepted. Player=%s Team=%s"),
        *GetNameSafe(Player), *TeamTag.ToString());
    return true;
}
```

현재 PlayerState는 GameMode를 friend로 선언하고 있으므로 private인 SetPlayerTeam을 이 함수에서 호출할 수 있다. 이를 위해 SetPlayerTeam을 public으로 변경할 필요는 없다.

이 함수에서는 팀 시작점이 **설정되어 있는지**만 확인한다. 지금 비어 있는지는 이후 ChoosePlayerStart에서 검사한다. 시작점은 있지만 다른 캐릭터가 점유 중이면 팀 승인은 유지하고 최초 스폰 재시도로 이어진다. 아직 팀을 기록하기 전인 여기에서 ChoosePlayerStart를 호출하면 None 팀 검사에 걸리므로 시작점 존재 여부를 직접 검사한다.

이 예시는 가이드용이며 소스에 적용하거나 빌드 검증하지 않았다. 다음 단계의 ServerRequestTeamSelection에서는 Player 인자로 클라이언트가 보내는 별도 포인터를 받지 않고 `this`를 전달한다.

Controller가 보낸 PlayerState 포인터를 신뢰하지 말고, RPC를 받은 Controller 자신에게 연결된 PlayerState를 서버에서 가져온다.

선택은 한 번만 승인한다. 같은 팀 재요청도 두 번째 성공으로 처리하여 Pawn을 또 생성하지 않는다. 서버 게임 스레드에서 팀 저장까지 동기적으로 끝내므로 뒤이어 들어온 요청은 HasAssignedTeam 검사에서 차단된다.

### 승인 후 스폰 실패 정책

팀이 승인되면 **스폰 실패 시에도 팀을 유지**한다. None으로 되돌려 다른 팀을 다시 선택하게 하지 않는다.

재시도는 별도 '입장 재시도' 동작으로 둔다. 최초 입장 중인 Controller에 대해 서버 전용 `bInitialSpawnPending` 같은 상태 하나를 보관하여 다음 조건에서만 허용한다.

```text
팀이 이미 승인됨
AND 최초 입장 스폰이 아직 성공하지 않음
AND 현재 Pawn이 없음
```

스폰 성공 시 서버의 이 상태를 해제한다. 사망 후 Pawn이 없는 순간을 최초 입장 재시도로 오인하여 리스폰 대기 시간을 우회하지 않게 한다. 기존 지연 리스폰은 별도 경로를 유지한다.

**완료 확인:** None 요청·두 번째 팀 변경은 실패하고, 정상 선택은 PlayerState에 한 번 저장된다.

### ClientTeamSelectionResult

**[직접 구현 필요 — C++]** CPP에 `void AProject_Z_MultiPlayerController::ClientTeamSelectionResult_Implementation(bool bAccepted, bool bSpawnSucceeded, const FText& Message)` 본문을 아래 분기에 맞게 작성한다.

- 거절: 처리 중 상태 해제, 사유 표시, 아직 팀이 없으면 A/B 버튼 다시 활성화.
- 승인·스폰 성공: A/B 버튼은 계속 잠그고 '입장 준비 중' 표시. 로컬 Pawn 준비 확인 전에는 UI를 제거하지 않는다.
- 승인·스폰 실패: A/B 버튼은 잠근 채 '입장 재시도' 버튼과 사유 표시.
- 이미 전투 화면으로 전환됐다면 늦게 온 결과로 선택 UI를 다시 열지 않는다.

결과 처리 시 bRequestPending을 해제하고 TeamSelectionMessage를 갱신한다. bTeamSelectionAccepted는 한번 true가 되면 뒤늦은 중복 요청 거절로 false로 되돌리지 않는다. 서버 승인 여부와 이미 복제된 팀 정보를 함께 확인하여 선택 버튼이 다시 열리지 않게 한다. bCanRetryInitialSpawn은 승인 후 스폰 실패 상태에서만 활성화한다.

로컬 UI 상태 bool은 서버 보안 검사나 PlayerTeam의 대체물이 아니다. UI에서 버튼이 비활성화돼 있어도 서버는 모든 요청을 검사한다.

## 9. 5단계 — 최소 팀 선택 Widget 만들기

### 9.1 C++ 기반 클래스

**[선행 코드 재사용 / BP 이벤트 직접 구현 필요]** 전체 클래스 헤더는 4.2에서 먼저 준비한다. 아래는 해당 이벤트 선언을 다시 설명한 것이므로 중복 추가하지 않는다. `ApplySelectionState`는 BlueprintImplementableEvent이므로 C++ 함수 본문이나 `_Implementation`을 작성하지 않고, 9.2의 WBP 이벤트 그래프에서 구현한다.

`UZTeamSelectionWidget : public UUserWidget`를 만들고, 표시 상태 적용용 Blueprint 이벤트만 제공한다.

```cpp
UFUNCTION(BlueprintImplementableEvent, Category = "Z|Team")
void ApplySelectionState(
    const FText& Message,
    bool bCanSelectTeam,
    bool bCanRetrySpawn);
```

이 함수는 C++에서 UI 상태를 전달하고 WBP에서 버튼·텍스트를 바꾸는 용도다. 서버 팀 결정 로직은 넣지 않는다. 버튼 바인딩은 이번 최소 구현에서는 WBP에서 처리하므로 C++에 Button 포인터들을 중복 추가할 필요가 없다.

### 9.2 WBP_TeamSelection 구성

**[직접 작업 필요 — BP/에디터]** 위젯 배치, 버튼 클릭 바인딩, ApplySelectionState 이벤트 그래프를 직접 작성한다.

Parent Class를 ZTeamSelectionWidget으로 지정하고 다음만 배치한다.

```text
Canvas Panel
 └─ 중앙 패널
     ├─ 제목: 팀 선택
     ├─ Button_TeamA
     ├─ Button_TeamB
     ├─ Text_Status
     └─ Button_RetrySpawn — 기본 숨김
```

각 버튼 OnClicked:

```text
Get Owning Player
 → Cast to Project_Z_MultiPlayerController
 → A/B: RequestTeamSelection(TeamA 또는 TeamB)
 → 재시도: RequestInitialSpawnRetry()
```

GetPlayerController(0) 대신 Owning Player를 사용한다. Widget은 네트워크 RPC 소유자가 아니므로 Controller를 통해 요청한다.

ApplySelectionState 이벤트에서는 상태 메시지 표시, A/B 버튼 IsEnabled 설정, 재시도 버튼 표시·활성화를 처리한다. C++와 BP 양쪽에서 같은 클릭을 중복 바인딩하지 않는다.

팀 인원 숫자는 필수 입장 흐름 검증 후 기존 GetTeamPlayerCount로 추가해도 된다. 클라이언트 인원은 복제 지연이 있으므로 입장 허용 판단에는 사용하지 않는다.

## 10. 6단계 — 선택 화면 생성 및 전투 HUD 전환

**선행 조건:** 4.2의 Widget 클래스, 4.3의 멤버/함수 선언, 8절의 요청·결과 처리 본문을 준비한다. 9.2에서 WBP 이벤트를 연결해야 실제 버튼/문구가 갱신된다. 아래 UI 함수 본문은 직접 구현해야 한다.

### 10.1 Controller의 최소 UI 멤버

**[선행 선언 재사용]** 실제 선언과 초기값은 4.3에 모았다. 아래는 각 멤버의 의미를 설명하는 부분이므로 같은 선언을 다시 추가하지 않는다.

```cpp
UPROPERTY(EditDefaultsOnly, Category = "Z|Team|UI")
TSubclassOf<UZTeamSelectionWidget> TeamSelectionWidgetClass;

UPROPERTY(Transient)
TObjectPtr<UZTeamSelectionWidget> TeamSelectionWidget;
```

로컬 최초 입장 완료, 요청 처리 중, 승인 응답 수신 여부는 필요한 bool로 구분한다. PlayerTeam을 Controller에 별도 복제 변수로 중복 저장하지 않는다. UI bool과 7절의 서버 bInitialSpawnPending은 서로 다른 목적이다.

직접 선언·초기화할 상태의 기준은 다음과 같다. 이름은 제안이며 같은 역할의 기존 변수가 있으면 재사용한다.

| 예시 멤버 | 초기값 | 사용 위치/목적 |
|---|---|---|
| bInitialEntryCompleted | false | 로컬: 최초 입장 완료 후 준비 검사 종료 |
| bRequestPending | false | 로컬: 선택/재시도 요청 중 중복 클릭 차단 |
| bTeamSelectionAccepted | false | 로컬: 승인 응답이 팀 복제보다 먼저 와도 선택 잠금 유지 |
| bCanRetryInitialSpawn | false | 로컬: 승인 후 스폰 실패 결과를 받았을 때 재시도 표시 |
| bInitialSpawnPending | false | 서버: 승인 후 최초 스폰 성공 전까지만 재시도 허용 |
| LastInitialSpawnRetryTime | -1.0 | 서버: 첫 요청은 허용하고 이후 요청 간격 검사 |
| TeamSelectionMessage | 빈 FText | 로컬: 결과/대기 메시지를 Tick 사이에 보관 |

이 상태들은 이번 설계에서 복제하지 않는다. 서버 상태는 서버에서만 변경하고, 로컬 표시 상태는 Client RPC 결과와 복제된 PlayerState/Pawn으로 갱신한다. 재시도 간격은 예를 들어 1초로 정하고, 첫 요청을 차단하지 않도록 초기값과 검사 조건을 함께 작성한다.

추가 함수 예:

```cpp
void ShowTeamSelectionUI();
void RefreshInitialEntryState();
void EnterGameplayUI();
```

### 10.2 BeginPlay 변경

**[직접 구현 필요 — C++]** BeginPlay 변경과 ShowTeamSelectionUI의 전체 본문은 직접 작성한다. 아래 CreateWidget과 입력 모드 코드는 함수 내부에 넣을 부분 예시이며 전체 구현이 아니다.

현재 `BeginPlay()`의 무조건 `CreateHUDWidget()` 호출을 제거하고 다음으로 교체한다.

```text
Super::BeginPlay()
로컬 Controller면 RefreshInitialEntryState()
```

PlayerState가 아직 도착하지 않았으면 데이터 준비 메시지를 표시하고 A/B 버튼은 잠근다. 준비될 때까지 팀을 임의로 None이라고 확정하여 요청하지 않는다.

ShowTeamSelectionUI는 Widget 생성과 화면 추가까지 담당하고 RefreshInitialEntryState를 다시 호출하지 않도록 작성한다. RefreshInitialEntryState가 ShowTeamSelectionUI를 호출하므로 반대로 호출하면 재귀가 생긴다.

ShowTeamSelectionUI는 로컬에서만 실행하고 Widget 중복 생성을 방지한다.

```cpp
TeamSelectionWidget = CreateWidget<UZTeamSelectionWidget>(
    this, TeamSelectionWidgetClass);
```

생성 성공 후 Viewport에 추가하고 UI 입력 모드를 설정한다.

```cpp
FInputModeUIOnly InputMode;
InputMode.SetWidgetToFocus(TeamSelectionWidget->TakeWidget());
SetInputMode(InputMode);
bShowMouseCursor = true;
```

Widget 클래스가 없거나 생성에 실패하면 오류 로그를 남긴다. Pawn을 임시 생성해 우회하지 않는다. Controller BP의 Class Defaults에서 TeamSelectionWidgetClass를 지정하여 해결한다.

### 10.3 네트워크 도착 순서에 독립적인 준비 검사

**[직접 구현 필요 — C++]** 기존 Tick 본문을 변경하고 `RefreshInitialEntryState()`를 새로 구현한다. 아래는 실행 순서다.

이번 최소 구현에서는 이미 존재하는 Controller Tick을 **최초 전투 진입 전까지만** 사용해 준비 상태를 확인할 수 있다. 새 타이머·델리게이트 계층을 필수로 추가하지 않는다.

```text
Tick:
  Super::Tick
  로컬 Controller이고 최초 입장 완료 전이면 RefreshInitialEntryState
```

RefreshInitialEntryState의 우선순위:

```text
유효한 MultiPlayerState가 없으면 대기
PlayerState에 팀이 있고, 소유한 FPS Pawn이 유효하며 시작 준비가 끝났으면 EnterGameplayUI
팀은 있지만 Pawn이 없으면 입장 대기/실패 UI 유지
팀이 없으면 선택 UI 유지
```

선택 버튼 활성 조건은 `PlayerState 유효 && 팀 없음 && !bTeamSelectionAccepted && !bRequestPending`이다. 재시도 버튼은 `bCanRetryInitialSpawn && !bRequestPending`일 때만 활성화한다. 준비가 끝나지 않았다는 이유로 RPC에서 받은 실패 메시지나 승인 상태를 매 Tick 초기화하지 않는다. Widget 유효성을 확인한 뒤 ApplySelectionState를 호출한다.

FPS Pawn의 BeginPlay 완료 여부도 확인하여 아직 초기화 전인 Pawn으로 HUD를 만들지 않는다. 성공 응답이 먼저 왔거나 팀 복제가 먼저 와도 최종 조건이 충족될 때까지 대기한다. 매 Tick Widget을 만들거나 SetInputMode·포커스를 반복 설정하지 않는다. 화면 상태가 전환될 때만 적용한다.

최초 입장 완료 후에는 이 검사 루프를 실행하지 않는다. 사망해 Pawn이 없어졌다고 다시 팀 선택 화면을 열지 않는다. 이미 유지 중인 전투 HUD는 기존 Pawn 조회 방식과 리스폰 동작을 사용한다.

### 10.4 EnterGameplayUI

**[직접 구현 필요 — C++]** 아래 순서로 함수 본문을 작성한다. 로컬 Controller 검사와 중복 진입 방지를 포함한다.

```text
로컬 최초 입장 완료 플래그 설정
선택 Widget RemoveFromParent, 참조 정리
FInputModeGameOnly 적용
bShowMouseCursor = false
기존 CreateHUDWidget 호출
이미 HUD가 있으면 표시 상태 복구
```

기존 CreateHUDWidget은 중복 생성 방지를 갖고 있으므로 재사용한다. 선택 화면용 코드에 적 HPBar 생성 경로를 연결하지 않는다.

UI만으로 이동을 막는 방식에 의존하지 않는다. 선택 전에는 서버에 전투 Pawn이 없다는 규칙이 핵심이다. 초기 대기 배경은 단색 Widget으로 충분하며 관전자·로비 카메라는 별도 기능으로 추가하지 않는다.

## 11. 7단계 — 기존 리스폰 경로 연결

**[기존 코드 재사용 + 실패 대응 직접 구현 필요 — C++]** 정상 리스폰은 유지한다. 아래에 설명하는 실패 감지와 재시도 처리는 기존 코드에 자동으로 포함되는 것이 아니며, 별도로 작성해야 한다.

`HandlePlayerDeath()`에서 팀을 초기화하거나 다시 선택하게 만들지 않는다. 기존 흐름을 유지한다.

```text
기존 PlayerState 팀 유지
 → 지연 후 기존 Pawn UnPossess·Destroy
 → RestartPlayer(기존 Controller)
 → 기존 팀으로 PlayerStart 선택
 → 새 Pawn 소유
```

최초 입장용 UI 상태와 서버 bInitialSpawnPending을 사망 시 다시 활성화하지 않는다. 지연 리스폰을 입장 재시도 RPC로 우회하지 못하는지 확인한다.

스폰 실패 로그는 단순히 RestartPlayer를 호출했다는 메시지와 실제 Pawn 생성 성공을 구분한다. 시작점이 모두 점유됐거나 잘못 배치된 경우, 기존 지연 리스폰에도 제한된 재시도 또는 명시적인 실패 대응이 필요하다. 팀이 다른 시작점으로 임의 스폰시키지 않는다.

직접 구현할 실패 대응의 최소 기준: RestartPlayer 이후 실제 Pawn을 검사하고, 실패하면 오류를 기록한다. 자동 재시도를 추가한다면 서버에서만 횟수·간격을 제한하고, Controller 유효성과 이미 Pawn이 생겼는지를 매번 검사한다. 최초 입장용 RPC나 bInitialSpawnPending을 재사용하지 않는다. 이 문서에는 해당 재시도 함수의 C++ 본문은 제공하지 않는다.

## 14. 단계별 완료 지점과 진행 방식

1. **선행 작업:** 3절에서 팀 enum과 PlayerState의 조회/저장/복제 구현을 확인하고 빠진 항목을 먼저 추가한다.
2. 4.1의 선언과 5~7절의 GameMode 본문을 함께 작성한다. 5절 RestartPlayer는 6절 시작점 선택 구현에 의존한다.
3. 4.2의 Widget 클래스와 4.3의 Controller 선언·상태를 준비한다. 8절과 10절의 함수 본문은 직접 작성해야 하며 서로 호출하므로 한 묶음으로 진행한다.
4. Controller 함수가 준비된 후 9.2의 WBP 이벤트/버튼과 Controller BP의 Widget 클래스를 연결한다.
5. 11절에서 리스폰 실패 대응의 미구현 부분을 확인하고, 12절 테스트로 전체 흐름을 검증한다.

각 단계에서 실제 수정 코드를 확인한 뒤 다음으로 진행한다. 예시 함수 이름은 기존 선언과 충돌하지 않게 정리하고 같은 역할의 함수를 중복 생성하지 않는다. 팀 선택 기능 완료 여부는 코드 작성·빌드 성공과 실행 검증을 구분하여 기록한다.

이번 변경은 기존 과제의 자동 배정 대신 수동 선택 흐름을 추가하는 작업이다. 선택 UI 미관, 캐릭터 미리보기, 로비 시스템, 온라인 세션 검색까지 범위를 늘리지 않는다.

## 15. 공식 참고 자료

초기 플레이어 시작과 Pawn 생성 진입점의 역할은 [Epic: Game Mode and Game State](https://dev.epicgames.com/documentation/unreal-engine/game-mode-and-game-state-in-unreal-engine)를 참고했다. 이 프로젝트는 AGameModeBase를 상속한다.

HandleStartingNewPlayer, RestartPlayer, FindPlayerStart와 ChoosePlayerStart 등 선언은 [Epic: AGameModeBase API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/GameFramework/AGameModeBase?application_version=5.5)를 참고했다. 실제 작성 시 설치된 UE 버전의 GameModeBase.h와 override 시그니처를 대조한다. 문서 예시는 엔진 버전별 구현 전체를 대신하지 않는다.
