# 직무과제 완료 보고서2

## 1. 업무명

**Unreal Engine 기반 FPS 멀티플레이 샘플 구현 및 네트워크 구조 설계 역량 강화**

## 2. 진행 결과 (계획 대비 실제 달성 내용)

### 개발 목표

- 기존 Unity 멀티플레이 개발 경험을 Unreal의 서버 권한 및 상태 복제 구조에 적용하여 실무 구현 역량 강화
- Listen Server 기반 최대 6인, Team A / Team B FPS 멀티플레이 샘플 구현
- 이동·전투·사망·리스폰·팀 선택·HUD를 서버와 클라이언트의 역할에 맞게 연동
- 호스트·게스트 간 동작 차이 및 상태 불일치 문제 분석·해결

## 3. 성과 (기대효과 대비 달성 내용)

기존 Unity 멀티플레이 개발 경험을 바탕으로 Unreal Engine의 서버 권한 구조와 RPC·Replication·RepNotify를 적용하여 Listen Server 기반 팀 FPS 멀티플레이 샘플을 구현하고 검증했습니다. 기존 TPS 프로젝트의 공통 전투 코드를 활용하면서 접속·팀 선택·이동·전투·사망·리스폰·경기 종료·재경기·퇴장 및 재입장까지 주요 멀티플레이 경기 흐름을 구성했습니다.

GameMode·GameState·PlayerState·PlayerController·Character의 역할에 따라 서버 판정, 공유 경기 상태, 플레이어 유지 정보 및 로컬 UI 처리를 분리했습니다. 발사·재장전·아이템 습득 요청을 서버에서 검사하고, 서버에서 확정한 전투 및 경기 상태를 복제하여 관련 클라이언트에 반영하도록 구성했습니다. 특히 Pawn 교체 시 유지할 팀 정보와 재경기 시 초기화할 상태를 구분하여 Unreal의 객체 생명주기에 맞는 경기 상태 관리 구조를 적용했습니다.

호스트와 게스트 간 이동·피격·HUD 동작 차이 및 입장·재경기 과정의 상태 불일치 문제를 입력, 서버 처리, 상태 복제, 로컬 표시 단계로 구분하여 조사하고 수정했습니다. 재경기에서는 기존 접속과 객체를 유지하면서 경기 상태를 초기화하고, 클라이언트 준비 확인과 이전 경기 예약 작업 무효화를 적용했습니다. 이를 통해 기존 네트워크 개발 경험을 Unreal의 클래스 구조와 복제·생명주기 관리 방식으로 확장하고, 멀티플레이 상태 불일치 원인을 분석하고 해결하는 실무 역량을 강화했습니다.

## 5. 업무결과 (결과물)

### 아키텍처

- **구현 방식:** C++ 핵심 로직과 Blueprint 시각적 효과·설정 분리
- **캐릭터 구조:** 기존 공통 캐릭터 코드를 재사용하면서 멀티플레이 전투와 FPS·TPS별 입력·표현 기능 분리. `ZCharacterBase → ZCharacterMulti → ZCharacterFPS / ZCharacterTPS` 계열
- **MultiGameMode:** 서버 팀 승인·스폰·리스폰·점수·경기 규칙
- **MultiGameState:** 팀 점수·남은 시간·경기 단계·승리 팀 등 공유 상태 복제
- **MultiPlayerState:** 팀 정보 저장·복제 및 일반 리스폰 시 유지
- **MultiPlayerController:** 소유 플레이어의 서버 요청·로컬 HUD·메뉴
- **Character / WeaponDataAsset:** 캐릭터 현재 전투 상태와 무기 기본 설정 분리
- **Projectile / ActorPoolSubsystem:** 충돌·피해 판정과 발사체 객체 재사용

### 5-1. 아키텍처 구현을 통한 역량 향상

**수행 내용**

- GameMode에서 팀 선택·스폰, GameState에서 점수·시간, PlayerState에서 팀 정보, Controller에서 서버 요청·로컬 UI 처리
- 캐릭터 사망·리스폰 이후에도 팀을 유지하도록 PlayerState 사용
- 로컬 UI·서버 판정·상태 복제 시점 분리
- `ZCharacterBaseMulti`에 공통 전투·재장전·피해 처리, `ZCharacter_FPS`에 카메라·조준·무기 습득 처리

**향상된 실무 역량**

- 기존 Unity 네트워크 개발 경험을 Unreal의 서버 권한과 클래스별 책임 구조에 적용하는 설계 역량 강화
- 서버 결정 상태·전체 공유 상태·Pawn 교체 후 유지 상태의 저장 위치와 생명주기를 구분하는 역량 확보

**주요 클래스 및 함수**

- `AProject_Z_MultiGameMode`: `TrySelectPlayerTeam()`, `RestartPlayer()`, `RegisterPlayerKill()`
- `AProject_Z_MultiGameState`: `TeamAScore`, `TeamBScore`, `MatchPhase`
- `AProject_Z_MultiPlayerState`: `PlayerTeam`, `OnRep_PlayerTeam()`
- `AProject_Z_MultiPlayerController`: `RequestTeamSelection()`, `CreateHUDWidget()`
- `AZCharacterBaseMulti`: 공통 전투·재장전·피해·사망
- `AZCharacter_FPS`: FPS 입력·ADS·무기 습득·마커 표시

**팀 입장 흐름**

팀 선택 UI → Controller 서버 RPC → GameMode 팀 승인 → PlayerState 팀 저장·복제 → 팀 시작점 주변 스폰 위치 탐색 → Pawn 준비 및 HUD 전환

- 공간이 부족하면 대기열 등록 후 기본 0.5초 간격으로 재탐색

### 5-5. 경기 진행·리스폰 구현을 통한 역량 향상

**수행 내용**

- Waiting → Playing → Finished 경기 단계 구성
- 기본 120초 제한 시간, 시간 종료 시 점수 비교, 경기 중 한 팀 전원 이탈 시 남은 팀 승리
- 서버 사망 판정 및 기본 3초 지연 리스폰, PlayerState 팀 정보 유지
- 팀 시작점 주변 빈 공간 탐색 및 혼잡 시 대기·재시도
- 접속·Controller·PlayerState를 유지한 채 팀·점수·시간·Pawn·픽업·UI·예약 작업 초기화 후 팀 선택부터 재경기
- 초기화 번호·팀 None·Pawn 없음 등을 확인하는 클라이언트 준비 응답 및 이전 경기 예약 작업 무효화
- 게스트 퇴장 시 호스트 방 유지, 호스트 퇴장 시 방 종료, 로컬 접속 메뉴에서 재입장

**향상된 실무 역량**

- Pawn 교체 시 유지 데이터와 초기화할 전투 상태를 구분하는 객체 생명주기 관리 역량 강화
- 접속과 기존 객체를 유지하면서 경기 데이터를 초기화하고 재경기 흐름을 구성하는 역량 확보
- 서버 초기화와 클라이언트 반영 시점 차이 및 이전 예약 작업의 영향을 고려해 경기 상태 불일치를 방지하는 처리 역량 강화

**경기 시작 조건**

- Waiting 단계이며 초기화 중이 아닐 것
- 초기화 준비 응답 대기가 없을 것
- 양 팀에 플레이어가 존재할 것
- 모든 Pawn의 스폰 완료를 기다리는 조건은 아님

## 제출 전 확인 사항

1. **최대 6인 검증:** 목표 인원과 실제 동시 테스트 인원·결과를 구분하여 기재한다.
2. **재접속 의미:** 신규 접속 후 현재 경기 상태를 복제하는 처리와 이전 플레이어의 상태를 식별·복원하는 처리를 구분한다. '점수 및 유저 상황 복사본 적용'의 실제 범위를 확인한다.
3. **업무일정:** 10월 27일 이후 수행한 재경기·픽업 등 작업이 있다면 실제 날짜를 추가한다.
4. **샷건 예외 처리:** 발사체 일부 생성 실패 시 탄약·피해 정책의 추가 검토를 완료된 정상 발사 기능과 분리한다.
5. **증빙 자료:** 서버 전투 요청 처리, 호스트·게스트 상태 불일치 수정 사례, 재경기 초기화 전후 비교 자료를 우선 확보한다. 자료 부족을 곧바로 기능 미완료로 해석하지 않는다.
