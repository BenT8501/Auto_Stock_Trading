## 1. 업무명

**Unreal Engine Listen Server 기반 팀 FPS 멀티플레이 구현 및 네트워크 기능 적용 역량 강화**

## 2. 진행 결과 — 계획 대비 달성 내용

### 개발 목표 및 구현 범위

기존 Unity 멀티플레이 개발 경험을 바탕으로 Unreal Engine의 네트워크 기능을 실제 게임 흐름에 적용하는 것을 목표로 했습니다. 기존 Project_Z의 캐릭터·무기·발사체 코드를 활용해 Team A / Team B로 나누어 플레이하는 FPS 샘플을 구현했습니다.

실제 네트워크 구성은 **호스트가 게임 서버와 자신의 플레이를 함께 실행하는 Listen Server 방식**입니다. 게스트는 호스트의 IP·포트로 접속하며, 전투와 경기 규칙의 최종 처리는 호스트의 서버에서 수행합니다. UE의 클라이언트·서버 네트워크 기능을 이용한 게임이며, 별도 서버 프로그램이나 통신 프로토콜을 직접 개발한 과제는 아닙니다. [Epic Games: 네트워크 개요](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine?application_version=5.7)

| 구분 | 달성 내용 |
|---|---|
| 접속 | Listen Server 방 생성, IP·포트로 게스트 입장, 퇴장 및 재입장 |
| 팀 입장 | 팀 선택 요청·서버 승인, 팀별 스폰, 스폰 공간 부족 시 대기·재시도 |
| 캐릭터 | 이동·점프·달리기, 1인칭 조준, 다른 플레이어의 조준 표현 |
| 전투 | 서버 발사 검사, Projectile 이동·충돌·피해 처리, 발사체 풀 재사용 |
| 무기 | 기본 권총 지급, 권총·소총·샷건 습득·교체, 동일 무기 공격력 강화 |
| 탄약·피해 | 서버 탄약 차감·재장전, 쉴드 우선 차감, HP 감소·사망·리스폰 |

| HUD | HP·쉴드·탄약, 소속 팀·팀 마커, 점수·남은 시간·경기 결과 |
| 경기 운영 | Waiting·Playing·Finished 단계, 제한 시간 종료, 한 팀 퇴장 시 승패 처리 |
| 재경기 | 접속 유지, 경기 상태 초기화, 이전 경기 예약 작업 무효화, 클라이언트 준비 확인 |

**검증 범위:** 구현 기능은 2026-10-29 개발자의 검증 완료 확인을 기준으로 정리했습니다. 이번 문서 작성에서는 코드와 작업 이력을 대조했으며, 새로 빌드하거나 PIE를 실행하지 않았습니다. 최대 6인은 계획상의 목표이며, 동시 6인 접속·지연·패킷 손실·성능에 관한 정량 결과는 별도로 기록되어 있지 않습니다.

## 3. 성과 — 멀티플레이·네트워크 관점

### 3-1. UE의 서버 권한과 소유 관계를 적용한 게임 처리 구현

팀 선택·발사·재장전·무기 습득을 플레이어의 Controller 또는 Character에서 서버로 요청하고, 서버에서 조건을 검사한 뒤 처리하도록 연결했습니다. UE가 제공하는 RPC 전달 기능을 사용하면서, 프로젝트에서는 요청 시점·전달 인자·게임 규칙 검사·결과 처리를 구현했습니다.

이를 통해 기존에 알고 있던 클라이언트 요청·서버 처리 개념을 **UE의 Authority, Actor 소유 관계, Server RPC 실행 조건에 맞춰 적용한 경험**을 쌓았습니다. 로컬에서 조종하는 객체인지와 서버 권한이 있는 객체인지를 구분하고, 호스트에서 정상인 기능도 게스트 경로를 따로 확인해야 한다는 점을 실제 구현과 검증에 반영했습니다.

### 3-2. 일회성 표현과 유지해야 하는 상태를 구분한 동기화 구현

탄약·쉴드·무기·팀·점수·경기 단계는 서버의 현재 값을 복제하고, 공격·재장전 애니메이션 실행에는 Multicast RPC를 사용했습니다. 값이 전달되는 것만으로 화면이 완성되지 않으므로, 무기 변경 후 메시·애니메이션 갱신과 로컬 HUD 표시도 연결했습니다.

이 과정에서 **서버 값 변경, 클라이언트 복제 수신, 화면 갱신을 각각 확인하는 방법**을 익혔습니다. 특히 C++에서 서버 값을 바꾸는 경로와 클라이언트의 RepNotify 경로를 구분해, Listen Server 호스트와 게스트 모두 필요한 표현을 갱신하도록 구성했습니다.

### 3-3. 접속 중 객체 교체와 경기 초기화를 다루는 경험 확보

일반 리스폰에서는 Pawn을 교체해도 팀 정보가 유지되도록 하고, 재경기에서는 기존 접속을 유지하면서 팀·점수·시간·캐릭터·픽업을 초기화했습니다. 이전 경기의 리스폰 예약이 새 경기에 영향을 주지 않도록 세대 값을 검사하고, 클라이언트가 새 초기화 상태를 받은 뒤 준비 응답을 보내도록 구현했습니다.

이를 통해 **서버에서 초기화가 끝난 시점과 클라이언트가 그 상태를 확인한 시점이 다를 수 있음**을 다루었습니다. 단순히 값을 0으로 바꾸는 작업에서 나아가, 진행 중이던 타이머와 기존 객체, 접속자의 준비 상태까지 함께 관리하는 경험을 얻었습니다.

## 5. 업무결과 — 구현 내용과 향상된 업무 역량

Unreal Engine의 Listen Server를 이용해 팀 기반 FPS 멀티플레이 샘플을 구현했습니다. 서버 요청 처리·상태 복제·경기 진행은 C++로 구현하고, 캐릭터·무기·애니메이션 등의 설정은 Blueprint·데이터 에셋으로 구성했습니다.

**아키텍처**

서버 요청 처리·경기 진행·복제할 정보·로컬 화면 처리를 각 클래스의 역할에 맞춰 구성했습니다.

| 주요 클래스 | 멀티플레이에서 담당하는 역할 |
|---|---|
| `AProject_Z_MultiPlayerController` | 플레이어의 입장·팀 선택 요청, 로컬 메뉴·HUD, 초기화 준비 응답 |
| `AProject_Z_MultiGameMode` | 서버의 팀 승인·스폰·리스폰·처치 등록·경기 시작과 종료 |
| `AProject_Z_MultiGameState` | 팀 점수·남은 시간·경기 단계·승리 팀 복제, 재경기 초기화 |
| `AProject_Z_MultiPlayerState` | 승인된 팀 정보 저장·복제, 일반 리스폰 중 팀 유지 |
| `AZCharacterBase` | AbilitySystemComponent·AttributeSet 생성, BeginPlay에서 Ability Actor 정보 초기화, HP 등 속성 조회 함수 제공 |
| `AZCharacterBaseMulti` | 공통 서버 전투·피해·사망 처리, 무기·탄약·쉴드·사망 상태 복제 |
| `AZCharacter_FPS` | FPS 입력·카메라·조준, 달리기 요청, 무기 습득, 캐릭터 표시 연결 |
| `AZCharacter_TPS` | 공통 캐릭터 상속, 기존 TPS 조작·카메라·표현 유지 |

캐릭터 상속은 다음과 같이 구성했습니다. 기존 TPS와 FPS가 공통 전투 처리를 사용하고, 시점별 입력·표현은 각 자식 클래스에서 처리하도록 구분했습니다.

```text
ZCharacterBase
└─ ZCharacterBaseMulti
   ├─ ZCharacter_TPS
   └─ ZCharacter_FPS
```

**네트워크 처리 흐름**

팀 선택·발사·재장전 등의 입력 요청은 다음 흐름으로 연결했습니다.

```text
로컬 입력 → 소유 Controller·Character의 Server RPC
→ 서버 조건 검사·상태 변경 → 변수 복제로 클라이언트에 상태 반영
→ 로컬 HUD 조회·RepNotify 등으로 화면과 캐릭터 표현 갱신
```

공격·재장전 애니메이션 실행은 Multicast RPC로 전달하고, 탄약·쉴드·팀·점수 등 현재 값은 변수 복제로 반영했습니다. 각 기능의 검사 조건과 상세 처리 흐름은 아래 항목에서 설명합니다.

### 5-1. Listen Server 접속·팀 입장과 서버 요청 처리

#### 수행 내용

호스트의 방 생성과 게스트 접속을 UI에 연결하고, 접속 이후 팀 선택·서버 승인·캐릭터 생성·게임 입력 활성화까지 구현했습니다. 팀 선택 승인과 실제 Pawn 준비를 구분해, 로컬 Pawn이 준비된 뒤 HUD를 생성하고 캐릭터 조작을 받도록 했습니다.

#### 적용한 UE 네트워크 기능과 직접 구현한 부분

- **Listen Server와 Travel:** 엔진의 `OpenLevel(..., "listen")`으로 호스트를 열고, 게스트는 `ClientTravel()`로 호스트 주소에 접속합니다. 프로젝트에서는 Host·Join UI, 주소 처리, 접속 이후 팀 입장 흐름을 구현했습니다.
- **Authority와 로컬 제어 구분:** 서버 규칙은 서버 권한 경로에서 처리하고, HUD·커서·입력 모드는 해당 로컬 플레이어에서 처리했습니다. 호스트는 서버이면서 플레이어이므로 두 조건을 같은 의미로 사용하지 않았습니다.
- **소유 관계와 Server RPC:** 클라이언트는 자신의 Controller·Character를 통해 요청합니다. 서버 소유 월드 아이템을 클라이언트가 직접 변경하지 않고, 자신의 Character에서 아이템 참조를 전달한 뒤 서버가 검사하도록 했습니다. UE의 RPC 라우팅에는 Actor의 소유 연결이 영향을 줍니다. [Epic Games: Actor 소유 관계와 연결](https://dev.epicgames.com/documentation/en-us/unreal-engine/actor-owner-and-owning-connection-in-unreal-engine?application_version=5.7)
- **RPC별 실행 대상:** Server RPC는 서버의 대응 객체에서, Client RPC는 대상 소유 클라이언트에서, 서버가 호출한 NetMulticast는 서버와 관련 클라이언트에서 실행됩니다. 프로젝트에서는 팀 선택 요청·결과 전달·애니메이션 실행에 각각 적용했습니다. `Reliable`은 전달 신뢰성을 위한 설정이며, 서버의 게임 규칙 검사 통과까지 보장하지 않습니다. [Epic Games: RPC](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine?application_version=5.7)

#### 주요 로직 흐름

```text
접속 UI
 ├─ 호스트: HostMatch → OpenLevel(listen)
 └─ 게스트: JoinMatch → ClientTravel(호스트 IP·포트)
 → 엔진 접속 처리, Controller·PlayerState 준비
 → 로컬 팀 선택 UI
 → RequestTeamSelection → ServerRequestTeamSelection
 → GameMode::TrySelectPlayerTeam에서 요청 조건 검사
 → PlayerState::SetPlayerTeam → RestartPlayer
 → 팀 PlayerStart 주변의 유효한 위치 탐색·Pawn 생성
 → 로컬 팀·Pawn 준비 확인 → HUD 생성·게임 입력 활성화
```

#### 향상된 업무 역량 및 활용

UE가 접속과 RPC 전달을 제공하더라도 팀 승인·중복 선택 방지·Pawn 준비 확인은 게임에서 구현해야 함을 구체적으로 적용했습니다. 향후 로비 선택이나 상호작용 기능에서도 **누가 요청할 수 있는지, 서버가 무엇을 검사하는지, 어느 플레이어에게 결과를 알리는지**를 나누어 구현할 수 있는 기반을 확보했습니다.

### 5-2. 서버 전투·이동과 발사체 재사용

#### 수행 내용

발사·재장전·피해 결과는 서버에서 처리하고, 클라이언트는 입력 요청과 표현을 담당하도록 연결했습니다. 플레이어 피해는 Projectile의 서버 충돌을 기준으로 처리합니다. 조준 방향과 장애물 확인에 Trace를 사용하지만, Trace로 즉시 피해를 주는 Hitscan 방식은 아닙니다.

| 기능 | 프로젝트에서 구현한 서버 처리 |
|---|---|
| 발사 | 생존·재장전·탄약·발사 간격 등을 검사하고 발사체 획득·발사, 발사 성공 시 탄약 차감 |
| 샷건 | 무기 데이터의 발사체 수·퍼짐을 적용하고 같은 발사의 발사체끼리 충돌하지 않도록 처리 |
| 피해 | 발사체 활성·권한·중복 대상·장애물·팀 관계를 확인하고 쉴드부터 차감, 나머지는 HP에 적용 |
| 사망 | 사망 중복 처리 방지, 재장전 취소, 적 처치 점수 등록, 리스폰 예약 |
| 재장전 | 서버 타이머로 완료 시점을 관리하고, 완료 시 현재 탄약 갱신 |
| 무기 습득 | 서버에서 아이템과 실제 겹침 등을 검사하고 교체 또는 동일 무기 강화 후 아이템 제거 |

동일 무기는 기본 공격력의 10%씩 최대 3단계 강화하며, 다른 무기로 교체하면 강화와 탄약을 해당 무기의 초기 상태로 변경합니다. 쉴드 아이템은 서버에서 회복 가능량을 확인하고, 실제 회복이 발생한 경우 소비합니다.

#### 적용한 UE 기능과 직접 구현한 부분

**이동:** `ACharacter`·`UCharacterMovementComponent`의 기본 네트워크 이동을 사용했습니다. 이동 예측·서버 보정·다른 플레이어의 이동 보간을 직접 작성한 것은 아닙니다. 프로젝트에서는 입력을 연결하고, 달리기 시작·종료 시 로컬과 서버의 `MaxWalkSpeed`를 함께 변경하도록 `ServerSetRunning()`을 추가했습니다. [Epic Games: CharacterMovement 네트워크 이동](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine?application_version=5.7)

게스트의 달리기와 이동이 어색했던 문제에서는 입력 여부만 보지 않고 **로컬과 서버가 사용하는 이동 속도 조건이 같은지** 확인했습니다. 엔진 이동 기능을 사용하더라도 게임이 추가한 속도 변경 조건은 양쪽 처리에 반영해야 한다는 경험을 얻었습니다. 현재 구현은 달리기 RPC 방식이며, 커스텀 SavedMove를 통한 이동 예측 확장까지 구현한 범위는 아닙니다.

**발사체:** UE의 Actor·이동 복제와 ProjectileMovement를 이용하되, 실제 이동·충돌·피해는 서버에서 처리하도록 했습니다. 클라이언트는 복제된 위치와 활성 상태를 사용해 발사체를 표시합니다.

**객체 풀:** 기존 `ActorPoolSubsystem`을 재사용하고, 발사체 획득 시 피해 대상 기록·이동 상태·타이머·충돌 제외 대상을 초기화하도록 연결했습니다. 충돌·수명·거리 종료 시 반환하며, 이미 반환된 객체의 중복 반환을 막았습니다. 재경기에서는 이전 경기 발사체를 일괄 반환합니다. 풀 자체는 기존 기능이며, 이번 과제의 성과는 서버 전투 및 재경기 흐름에 맞게 적용·보완한 부분입니다.

**애니메이션:** 공격은 Unreliable Multicast, 재장전 시작·종료는 Reliable Multicast로 연결했습니다. 각 화면에서 Montage를 실행하는 표현과 서버 탄약 갱신을 분리했습니다. 무기 교체·사망 시에는 기존 재장전 타이머를 취소해 이후 콜백이 잘못된 탄약 상태를 변경하지 않도록 했습니다.

#### 주요 로직 흐름

```text
로컬 발사 입력 → ServerRequestFire → FirePrimaryProjectile
 → 서버 발사 조건 검사 → 풀에서 Projectile 획득·발사
 → 탄약 차감·공격 애니메이션 전달
 → 서버 Projectile 충돌·대상 검사 → ReceivePlayerDamage
 → 쉴드·HP 변경 → 필요 시 사망·점수·리스폰 처리
 → 변경 상태와 발사체 움직임을 관련 클라이언트에 복제
```

#### 향상된 업무 역량 및 활용

클라이언트에서 발사나 애니메이션이 보이는 것과 서버에서 피해·탄약 처리가 성공한 것을 구분해 확인했습니다. 향후 전투·스킬·상호작용 기능에서도 표현 성공만으로 처리 완료를 판단하지 않고, 서버의 조건 검사와 실제 상태 변경을 기준으로 구현·검증하는 데 활용할 수 있습니다.

### 5-3. 상태 복제와 로컬 HUD·캐릭터 표현 연결

#### 수행 내용

HP·쉴드·탄약·무기와 팀·경기 정보를 복제 대상으로 지정하고, 각 클라이언트에서 받은 값으로 HUD와 캐릭터 표현을 갱신했습니다. 화면의 Widget 자체를 서버에서 복제하는 방식이 아니라, 각 플레이어의 로컬 Widget이 복제된 게임 정보를 읽도록 했습니다.

| 정보 | 서버 처리·클라이언트 반영·로컬 표시 |
|---|---|
| HP | 서버에서 `UZAttributeSet`의 HP를 변경하고 클라이언트에 복제. RepNotify 함수인 `OnRep_HP()`에서 GAS의 HP 변경 알림으로 연결. 이 알림에 등록한 `HandleHPAttributeChanged()`에서 HP 감소 시 대상 HP Bar 표시. 로컬 HUD는 현재·최대 HP를 조회해 비율 표시 |
| 쉴드 | 서버의 Character에 현재·최대 쉴드를 저장하고 변경값을 클라이언트에 복제. `OnRep_CurrentShield()`·`OnRep_MaxShield()`에서 `UpdateShieldVisual()`을 호출해 캐릭터의 보호막 표시 갱신. 로컬 HUD는 별도로 `RefreshCurrentStatus()`에서 쉴드 비율을 주기적으로 조회·표시 |
| 탄약 | 서버에서 발사·재장전 결과에 따라 `currentAmmo`를 변경하고 클라이언트에 복제. 로컬 HUD의 `RefreshCurrentStatus()`에서 현재 탄약값을 주기적으로 조회·표시 |
| 무기 | 서버에서 `CurrentWeaponData`를 변경하고 해당 참조를 클라이언트에 복제. 호스트 화면은 직접 호출로, 게스트 화면은 `OnRep_CurrentWeaponData()`로 무기 메시·애니메이션 갱신 |
| 소속 팀 | 서버의 GameMode에서 팀 선택 요청을 검사하고 PlayerState의 `PlayerTeam`을 저장·복제. `OnRep_PlayerTeam()`에서 팀 변경 델리게이트 실행. 로컬 팀 HUD는 `RefreshTeamStatus()`, 캐릭터 마커는 `UpdateTeamMarkerPresentation()`에서 팀 정보를 주기적으로 조회·표시 |
| 점수 | 서버의 GameMode에서 처치 점수를 등록하고 GameState의 팀 점수를 변경·복제. `OnRep_TeamScores()`에서 점수 변경 델리게이트 실행. 로컬 팀 HUD는 별도로 `RefreshTeamStatus()`에서 점수를 주기적으로 조회·표시 |
| 남은 시간 | 서버의 GameMode 타이머에서 남은 시간을 갱신하고 GameState를 통해 클라이언트에 복제. 로컬 팀 HUD의 `RefreshTeamStatus()`에서 남은 시간을 주기적으로 조회해 타이머 표시 |
| 경기 결과 | 서버의 GameMode에서 승패를 결정하고 GameState의 경기 단계·승리 팀을 저장·복제. 로컬 PlayerController의 Tick에서 경기 종료 상태를 검사하고 `ShowMatchResult()`를 호출해 점수·승리 팀을 결과 UI에 표시 |

#### 복제 설정과 OnRep 처리

C++ 클래스의 `UPROPERTY`에 `Replicated` 또는 `ReplicatedUsing`을 지정하고, `GetLifetimeReplicatedProps()`의 `DOREPLIFETIME` 계열 매크로로 복제할 변수를 등록했습니다. 복제 후 실행할 처리는 `ReplicatedUsing`에 OnRep 함수를 지정해 연결했습니다. [Epic Games: Actor 속성 복제](https://dev.epicgames.com/documentation/en-us/unreal-engine/replicate-actor-properties-in-unreal-engine?application_version=5.7)

C++에서 서버의 변수값을 변경하는 것만으로 서버 OnRep가 자동 호출되지는 않습니다. 따라서 무기 교체 시 호스트 화면은 갱신 함수를 직접 호출하고, 게스트 화면은 복제 수신 후 `OnRep_CurrentWeaponData()`에서 같은 갱신 함수를 호출하도록 구현했습니다.

#### 주요 로직 흐름

```text
서버 무기 습득 검사·승인 → CurrentWeaponData 변경
 ├─ 서버: 무기 메시·애니메이션 직접 갱신
 └─ 원격 클라이언트: 참조 복제 수신
     → OnRep_CurrentWeaponData
     → EquipWeaponVisual·RefreshCharacterAnimation
로컬 HUD는 해당 Pawn의 현재 무기·탄약 값을 조회해 표시
```

#### 향상된 업무 역량 및 활용

Unreal Engine의 상태 복제와 RepNotify·Attribute 변경 알림을 이용해 서버의 변경값을 로컬 HUD·캐릭터 표시에 연결했습니다. 복제 후 알림으로 실행할 처리와 HUD에서 값을 주기적으로 조회할 처리를 구분해, 멀티플레이 상태 정보와 화면 갱신을 연결하는 방법을 익혔습니다.

### 5-4. 리스폰·경기 종료·재경기·퇴장 처리

#### 수행 내용

서버가 경기 시간을 진행하고, 종료 시 점수를 비교해 승리 팀 또는 무승부를 결정하도록 했습니다. 기본 제한 시간은 120초이며 설정으로 조절할 수 있습니다. 경기 도중 한 팀의 인원이 없어지면 서버가 남은 팀 기준으로 종료를 처리합니다.

일반 리스폰은 사망 후 기본 3초 뒤 서버가 예약 실행합니다. 팀별 PlayerStart 주변에서 바닥·높이·캡슐 충돌을 확인하고 생성하며, 공간이 부족하면 대기열과 재시도 타이머로 처리합니다. PlayerState의 팀 정보는 유지하고 Pawn은 새로 생성합니다.

재경기는 호스트의 요청을 서버가 검사한 뒤 기존 연결·Controller·PlayerState를 유지한 상태에서 진행합니다. 맵을 다시 여는 것만으로 초기화하지 않고, 이전 경기의 작업과 상태를 명시적으로 정리했습니다.

#### 주요 로직 흐름과 초기화 구분

```text
RestartMatch → RestartMatchForHost
 → 초기화 중 요청 제한·MatchGeneration 증가
 → 이전 경기 타이머 정리·발사체 풀 반환·픽업 제거
 → 재장전 취소·기존 Pawn 제거·팀 초기화
 → GameState::ResetForNewMatch
     점수·시간·경기 단계·승리 팀 초기화, MatchResetSerial 증가
 → Controller별 준비 대기 설정·ClientPrepareNewMatch 전달
 → 클라이언트가 새 초기화 상태 확인 후 준비 응답
 → 팀 재선택·스폰 및 경기 시작 조건 재확인
```

| 관리 값 | 목적 |
|---|---|
| `MatchGeneration` | 서버의 이전 경기 리스폰 예약을 구분하고, 지난 경기 콜백을 무효화 |
| `MatchResetSerial` | 클라이언트가 어느 경기 초기화 상태를 받았는지 확인하고, 해당 번호의 준비 응답인지 검사 |

새 경기 시작 조건은 **Waiting 상태, 초기화 중이 아님, 준비 응답 대기자가 없음, 양 팀에 인원이 있음**입니다. 모든 새 Pawn의 생성 완료를 기다리는 조건으로 구현한 것은 아닙니다.

픽업은 배치된 생성 지점마다 초기 생성하고, 습득한 지점은 기본 10초 뒤 다시 생성하도록 했습니다. 재경기에서는 기존 픽업과 관련 예약을 정리한 뒤 새 경기의 픽업을 생성합니다.

#### 퇴장·재접속 처리

게스트가 퇴장하면 해당 접속만 종료하고 호스트의 방은 유지합니다. 호스트가 퇴장하면 연결된 게스트도 입장 화면으로 돌아가도록 처리합니다. 재접속 시에는 호스트의 실제 IP·포트로 다시 접속해야 하며, 같은 맵을 로컬에서 여는 것만으로 같은 방에 들어가는 것은 아닙니다. PIE에서는 실행 환경에 따라 실제 포트가 달라질 수 있어 연결 주소를 확인하도록 했습니다.

현재 재접속은 방에 다시 입장하는 기능이며, 이전 캐릭터의 무기·체력·개인 진행 정보를 저장해 복원하는 영속 재접속 기능까지 구현한 범위는 아닙니다.

#### 향상된 업무 역량 및 활용

리스폰에서 유지할 팀 정보와 재경기에서 초기화할 팀·점수·캐릭터 정보를 구분하고, 서버 예약 작업과 클라이언트 준비 상태를 함께 관리했습니다. 향후 라운드 전환이나 재입장 기능에서도 오래된 콜백 차단, 객체 정리, 초기화 수신 확인을 별도 확인 항목으로 적용할 수 있습니다.
