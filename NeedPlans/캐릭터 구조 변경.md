# Project_Z 캐릭터 공통화 설계 검토 컨텍스트

## 1. 검토 목적

기존 Unreal 프로젝트에서 TPS와 FPS가 공유할 변수·함수·컴포넌트·데이터 참조를 `ZCharacterBaseMulti`로 옮기는 작업을 준비 중이다.

기존 코드와 의존성을 확인하여 다음을 검토해 달라.

- 부모로 이동할 항목
- 공통 부분을 분리한 뒤 이동할 항목
- 자식에 유지할 항목
- 캐릭터 밖의 기존 시스템에 유지할 항목
- 이동에 따른 초기화·입력·애니메이션·네트워크 문제

단순한 일반론이나 새로운 프레임워크 제안보다, 기존 코드를 근거로 구체적인 목록과 순서를 제시해야 한다.

## 2. 작업 방식과 제약

- 사용자가 직접 수정한다. 에이전트는 코드를 읽고 가이드만 제공한다.
- 코드·파일 수정, 빌드, 실행은 하지 않는다.
- Git pull은 별도 요청이 있을 때만 진행한다.
- 의존성 검토를 끝낸 뒤 정리된 답변을 제공한다.
- 실제 코드에 있는 기능을 새로 만들자고 제안하지 않는다.
- 새 Actor/Component 체계 도입 등 불필요한 구조 확장은 피한다.
- 확인하지 않은 Blueprint 설정은 사실로 단정하지 않는다.
- 기존 TPS 동작을 유지하면서 단계적으로 공통화한다.

## 4. 사용자 의도와 클래스 구조

사용자가 설명한 목표 구조:

ZCharacterBase
├─ ZEnemyBase
└─ ZCharacterBaseMulti
   ├─ ZCharacter_TPS
   └─ ZCharacter_FPS

- ZCharacterBase:
  AbilitySystemComponent, AttributeSet 등 기초 기능
- ZCharacterBaseMulti:
  TPS/FPS 공통 무기·투사체 발사·탄약·재장전·애니메이션·공통 입력·피해 처리
- TPS/FPS:
  각 시점의 카메라·조준·표현 및 장르 고유 처리

TPS와 FPS가 ZCharacterBaseMulti를 상속하는 것은 코드로 확인했다.
ZEnemyBase의 실제 상속은 이번 검토에서 별도로 확인할 것.

과제 계획에서는 GAS 추가 학습·구현을 제외했지만,
실제 기존 코드에는 ASC·AttributeSet·GAS 피해 처리가 남아 있다.
기존 GAS 코드를 임의로 제거하지 말고 현재 의존성을 기준으로 검토할 것.

## 5. 현재 진행 상태

- FPS 이동·카메라·기본 네트워크 실험 구현
- HUD 및 HPBar 연결
- 테스트 키로 서버에서 자기 캐릭터에게 피해 적용
- 피해 시 HPBar 표시 및 마지막 피해부터 3초 후 숨김 확인
- HPBar 위치·방향은 일단 사용 가능한 상태
- 사망 시 HPBar 정리는 실제 총기 피해 연결 후 확인 예정

조준 보조용 Trace와 실제 Hitscan 피해 판정을 구분할 것.

## 8. 입력·발사 책임에 대한 합의

공통 발사 입력과 투사체 획득·발사는 부모에 둔다.
자식에 투사체 생성 코드를 중복 작성하지 않는다.

목표 흐름:

부모의 공통 발사 입력
→ 로컬 조준 정보 확보
→ 서버 발사 요청·검증
→ 부모의 공통 Projectile 발사 처리
→ PoolSubsystem에서 투사체 획득
→ 발사자·피해·속도·사거리 등 설정
→ 발사

TPS/FPS는 시점별 조준 계산을 가상 함수로 제공하는 방향이다.

주의:
- 서버에서 원격 플레이어의 로컬 카메라를 직접 조회한다고 가정하지 말 것.
- 조준 정보 전달·검증 방식은 아직 구현 확정 전이다.
- 공통화와 네트워크 완성은 별개 작업이다.

## 10. 이미 확인된 분리 필요 지점

### 무기 조회·초기화
GetActiveWeaponData는 CurrentWeaponData가 없으면
CharacterDataAsset의 DefaultWeaponData를 참조한다.

GetActiveWeaponData만 단독 이동하면 안 된다.
기본 무기 초기화와 부모·자식 BeginPlay 실행 순서를 함께 검토해야 한다.

### 탄약
현재 GetDefultAmmo 계산:
DefultAmmo + LevelUpAmmoCount × 현재 레벨
이후 MaxAmmo로 상한 제한

따라서 현재 MaxAmmo는 코드 사용상 성장 탄창 용량의 상한이며,
예비 탄약 수라고 해석하면 안 된다.

GetMaxAmmo/GetDefultAmmo는 CurrentWeaponData null 처리도 점검할 것.

### 장착
EquipWeaponVisual과 EquipWeaponFromPickup에 부착 코드가 중복돼 있다.

장착 소켓은 WeaponData.AttachSocketName을 우선 사용하고,
없으면 CurrentData.AttachSocketName을 사용한다.

공통 장착 함수와 TPS 픽업 처리의 책임을 나눌 것.

### 총구
GetProjectileSpawnLocation에는 다음이 혼재한다.

- 무기 소켓 조회
- Rifle/Shotgun별 고정 위치 보정
- 캐릭터 소켓 대체
- FollowCamera 대체
- Actor 위치 대체

WeaponData null 검사 없이 AnimationType을 읽는 부분이 있다.
StaticMesh 무기의 총구 조회 지원도 확인할 것.

### 애니메이션·무기 상태
RefreshWeaponState에는 다음이 혼재한다.

- 애니메이션 갱신
- 무기 장착·해제
- 연사 중단
- 속성 효과
- 변경 감지
- TPS Controller의 조준점 표시

UnequipWeaponVisual에는 Niagara 속성 효과 정리가 섞여 있다.

ApplyResolvedCharacterData에는 공통 Mesh·능력치 설정과
TPS 메타 성장 적용 기록 초기화가 섞여 있다.

### 입력
TPS와 FPS에 DefaultIMC가 각각 있다.
공통 부모에 옮길 때 중복 선언·에셋 설정을 처리해야 한다.

TPS:
IA_Jump, IA_Ability_Primary, IA_Ability_Secondary 등

FPS:
JumpAction, ActionFire, ActionReload 등

FPS의 Fire/Reload는 마지막 확인 시 입력 로그만 출력했다.
TPS Reload를 부모로 옮길 때 FPS Reload가 숨기거나 충돌하지 않도록
입력 진입점과 공통 실행 함수 이름·역할을 정리해야 한다.

### 재장전 Notify
ZAnimNotify_ReloadAmmo는 현재 TPS로 캐스팅해서 FinishReload를 호출한다.

부모 공통 함수로 변경할 경우:
- 호출 타입 변경
- 서버 권한
- 재장전 상태
- 중복 Notify 처리
를 함께 검토해야 한다.

## 11. 풀·Projectile에서 확인한 연결 문제

UZActorPoolSubsystem은 UWorldSubsystem으로 이미 분리돼 있다.
풀 자체를 캐릭터 부모로 이동하지 않는다.

현재 TPS 발사:
GetWorld()->GetSubsystem<UZActorPoolSubsystem>()
→ AcquireProjectile()
→ Owner·피해·관통·속성 설정
→ LaunchInDirection()
→ SetReturnDistance()

검토 사항:
- LaunchInDirection에서 거리 검사 타이머를 설정하므로,
  SetReturnDistance가 발사 뒤에 있는 순서 점검
- 풀 획득 과정에서 충돌을 활성화한 뒤,
  호출자가 Owner·데이터를 설정하는 순서 점검
- 재사용 시 이전 Owner·상태·타이머·데이터 잔존 여부
- 서버의 게임 판정과 클라이언트 투사체 표현·풀 수명 동기화

Projectile 충돌 처리:
- ZDamageableInterface 구현 대상을 검사
- GAS 피해 적용을 먼저 시도
- 실패하면 인터페이스 ReceiveDamage 호출
- AZEnemyBase 전용 속성 반응 처리도 포함

현재 캐릭터 C++ 상속 선언에서는 ZDamageableInterface 구현을
확인하지 못했다. Blueprint 구현 여부는 확인 필요.

FPS 테스트의 ReceiveEnemyDamage 직접 호출과
실제 Projectile 충돌 피해 경로는 다르다.
총알이 플레이어에게 피해·HPBar·사망 반응까지 전달되는지 연결을 검토할 것.

## 13. 원하는 검토 결과 형식

먼저 현재 코드에서 제안 구조의 문제점·누락을 짧게 설명한다.
그다음 실제 이동 목록을 다음 순서로 제시한다.

1. ZCharacterBaseMulti.h에 필요한 include
2. 전방 선언할 class / struct
3. 부모로 옮길 변수
4. 부모로 옮길 함수 선언
5. ZCharacterBaseMulti.cpp에 필요한 include
6. 그대로 이동할 구현
7. 분리·수정 후 이동할 구현과 그 의존성
8. TPS에 유지할 항목
9. FPS에서 중복 제거·변경할 항목
10. AnimNotify·UI·Pickup·Ability 등 외부 호출부 변경
11. 단계별 작업 순서와 각 단계의 확인 기준

모든 항목은 실제 식별자와 근거 파일 위치로 설명한다.
부모로 옮기면 멀티플레이까지 자동 완성되는 것처럼 설명하지 않는다.
최종 목록을 내기 전에 호출 관계와 데이터 의존성을 끝까지 확인한다.
