## 1. 게임 개요

**GO ~! UP!!!!**은 최대 9명이 건설하며 위로 올라가고, 무기로 상대와 건축물을 공격해 자원을 확보하는 개인전 경주 게임이다. 60초마다 아래에서 올라오는 위험한 물을 피해 상승하고, 목표 높이에 먼저 도달하면 승리한다.

사용자는 UEFN과 로블록스 두 버전을 원한다. Roblox 버전은 Fortnite 기본 빌드 시스템을 그대로 호출하는 방식이 아니라 **발판·경사로 등 건설 조작을 자체 구현해 같은 게임 규칙을 만드는 방향**으로 계획한다. Fortnite의 자산·무기·UI가 자동으로 제공되거나 두 플랫폼의 코드가 호환된다고 가정하지 않는다.

```text
참가·시작 위치 배정 → 시작 상자 획득 → 건설·상승
  → 상대 또는 건축물 공격 → 자원·아이템 획득 → 추가 건설
  → 일정 높이에서 새 보물 상자 등장 → 상승 반복
  → 60초 주기의 물 상승 압박 → 목표 높이 최초 도달자 승리
```

## 4. 맵 설계 논의

| 안 | 장점 | 검증할 점 |
| :-- | :-- | :-- |
| 3×3 분리 구역 | 9명 배치와 거리 비교가 쉬움 | 중앙 집중 공격과 모서리의 유리함 |
| 원형 9개 구역 | 이웃 간 거리를 맞추기 쉬움 | 반대편 사격 거리, 중앙 다리 연결 |
| 공용 상승 공간 | 전투·루팅·건설 동선이 자주 겹침 | 시작 거리 조건과 초반 전투 과열 |

우선 두 구역과 낮은 골인 영역만 만들어 설치·사격·상승이 재미있는지 확인한 뒤 9명 맵으로 확장한다. 경로마다 시작 상자·보급 접근성·높이 조건을 비교한다.

- 가장 가까운 가장자리 사이 간격이 시작 이동 수단의 최대 이동 거리보다 커야 한다.
- 질주·점프·공중 도구 사용을 포함해 실제 이동 거리를 측정한다. 모델 크기나 육안으로 확정하지 않는다.
- 선택한 총의 유효 사거리 안에 상대 건축물이 있어야 한다. 명중뿐 아니라 피해량·가시성도 확인한다.
- 건설로 다리를 연결해 침입하는 것을 허용할지는 별도 결정이다.
- 목표 높이 단순 통과와 지정 골인 영역 진입을 구분한다. 임시로 지정 영역 진입을 제안한다.
- Roblox의 높이는 Y축, 거리 단위는 stud 기준으로 관리한다. UEFN의 Z축·cm·타일 숫자를 그대로 복사하지 않는다.
- 시작 자원으로 첫 보급 지점까지 도달 가능한지 계산한다. 처치를 못 하면 반드시 중간에 멈추는 구조가 되지 않도록 기본 자원 공급을 논의한다.

`필요 자원 ≈ 구간 상승에 필요한 구조물 수 × 설치 비용 + 방어·우회 여유분`

## 5. Roblox 구현 방향

Roblox Studio에서 서버 Script·ModuleScript와 클라이언트 LocalScript·UI를 나누어 구현한다. 아래 명칭은 **역할 초안**이며 생성된 클래스나 파일이 아니다. 초기부터 각 행마다 모듈을 하나씩 만들 필요는 없다.

| 기능 | 서버에서 처리할 내용 | 클라이언트에서 처리할 내용 |
| :-- | :-- | :-- |
| 경기 진행 | 참가자·경기 단계·목표·승자·종료 확정 | 안내·결과 화면 |
| 건설 | 설치 요청 검사, 자원 차감, 구조물 생성·HP·파괴 | 건설 종류 선택, 배치 미리보기, 회전·설치 입력 |
| 전투 | 장착·탄약·연사 간격·사거리·명중·피해 검사 | 조준·입력·효과·피격 안내 |
| 인벤토리 | 자원·아이템·무기·탄약의 실제 값 변경 | 현재 값과 수량 표시 |
| 상자 | 개봉 거리·생존·높이 보상 검사, 개봉 기록·지급 | 상호작용 안내·개봉 연출 |
| 전리품 | 사망 1회 확정, 이전 또는 드롭 생성·습득 처리 | 보상·드롭 표시 |
| 물 | 상승 단계·수위·위험 영역·피해 처리 | 수면 연출과 다음 상승 시간 표시 |
| 골인·재경기 | 유효 도달·최초 승자 확정, 이전 경기 정리 | 결과·다음 경기 UI |

### 저장 위치와 요청 전달 초안

- `ServerScriptService`: 경기·인벤토리·건설·전투·보상 처리. 클라이언트가 준 수량·피해량을 그대로 사용하지 않는다.
- `ServerStorage`: 서버가 생성할 구조물·드롭 등의 원본 후보.
- `ReplicatedStorage`: RemoteEvent, 공유 식별자·설정, 배치 미리보기용 모델 후보. 민감한 실제 인벤토리 표는 서버에서 관리한다.
- `Workspace`: 경기 맵·설치된 구조물·활성 상자·드롭·수면 표현.
- `StarterPlayerScripts` 또는 도구의 LocalScript: 입력·건설 미리보기·카메라·효과.
- `StarterGui`: 자원·무기·탄약·시간·결과 UI.
- 공개 경기 상태는 복제되는 속성 또는 이벤트로 알리고, 개인 인벤토리는 대상 플레이어에게 전달한다. UI 최초 생성·재생성 시 현재 상태를 받을 수 있게 한다.

RemoteEvent는 클라이언트 입력과 서버 처리 결과를 연결하는 수단으로 사용한다. 전달되는 데이터 형태와 한계는 공식 문서를 확인한다. [Remote events and callbacks](https://create.roblox.com/docs/scripting/events/remote)

설치·공격·습득 요청은 서버에서 거리·상태·빈도·대상을 검사한다. ProximityPrompt가 있다는 이유만으로 개봉 검증을 생략하지 않는다. [Securing the client-server boundary](https://create.roblox.com/docs/scripting/security/client-server-boundary)

### 건설 처리 흐름

```text
로컬 건축 종류·위치 선택 → 미리보기 → 설치 요청
  → 서버가 경기·생존·종류·수량·거리·격자·영역·충돌·지지 조건 검사
  → 겹치는 요청도 최종 설치 직전에 재검사
  → 성공 시 자원 차감과 구조물 생성 → 실제 구조물과 수량 전달
```

임시 방향은 고정된 부품으로 시작하는 것이다. 자원 차감 후 생성이 실패하면 값이 유실되지 않아야 한다. 서버 상태 확정 중 불필요한 대기를 넣어 중복 설치가 들어오지 않게 한다. 구조물마다 소유자·HP·경기 식별값·보상 가능 여부를 관리한다. 지지 연결 붕괴를 채택하면 별도 연결 관계 탐색과 연쇄 파괴 제한이 필요하다.

### 전투 처리 흐름

```text
발사 입력 → 서버 요청 → 장착·탄약·연사·조준 범위 검사
  → 명중 판정 → 플레이어 또는 건축물 피해
  → 사망·파괴 1회 처리 → 전리품 지급/드롭 → UI·효과 반영
```

첫 실험에서는 Raycast 총기 1종을 제안한다. 투사체 방식은 확정되지 않았으며 사용자의 선택에 따라 바꾼다. Raycast는 충돌 대상을 얻는 수단이고 사거리·엄폐·탄약 등의 게임 검사는 별도 구현한다. [Raycasting](https://create.roblox.com/docs/workspace/raycasting)

붕괴 부품을 물리적으로 떨어뜨리기로 하면 네트워크 소유권과 성능을 별도 확인한다. 초기에 많은 물리 부품을 떨어뜨리는 것을 전제로 하지 않는다. [Network ownership](https://create.roblox.com/docs/physics/network-ownership)

### 모든 아이템 획득

서버 인벤토리에서 사망자의 실제 아이템·자원·탄약·무기를 확정한 후 1회 이전하거나 드롭으로 전환한다. 자동 이전과 드롭은 동시에 실행해 보상이 복제되지 않게 한다. 무기 내부 탄약과 예비 탄약을 중복 계산하지 않고, 초과분 처리와 사망 원인에 따른 수령 대상을 먼저 정한다.

### 물과 시간

경기 시작을 기준으로 다음 상승 시각을 계산한다. 매 60초마다 물 단계를 증가시키고 정해진 높이로 상승시킨다. 시각적 상승이 부드럽다면 피해 수위도 같은 진행값을 사용한다. 물 밖에 나가면 피해가 멈추며 한 명에게 피해 루프가 중복 생성되지 않아야 한다.

고정 범위의 수면 모델은 표현용이며 서버는 별도로 맵 내부·수위·신체 기준점을 검사한다. 실제 Terrain 물과 수영 구현은 별도 선택 사항이다. UI는 플레이어마다 독립적인 60초 타이머를 만들지 않고 공통 상승 시각을 기준으로 표시한다.

## 6. 단계별 구현 계획

기간은 Studio·Luau 경험과 실험 결과를 확인한 후 산정한다. UEFN과 같은 기간으로 가정하지 않는다. 건설·전투·인벤토리를 자체 구현해야 하는 범위가 있다.

| 순서 | 주요 작업 | 하는 이유·완료 기준 |
| :-- | :-- | :-- |
| 0 | Studio 환경·프로젝트 위치 확인, 미정 규칙 협의 | 기존 프로젝트와 분리하고 실제로 만들 범위 확정 |
| 1 | 두 시작 구역·기본 이동·낮은 골인 영역 | 점프 거리·시야·맵 크기부터 검증 |
| 2 | 서버 인벤토리·시작 상자·기초 HUD | 건설·전투가 참조할 실제 자원·탄약 데이터 마련 |
| 3 | 발판·경사로 선택·미리보기·서버 설치·자원 소모 | 두 플레이어가 제한된 자원으로 목표 높이까지 올라갈 수 있음 |
| 4 | 총기 1종·탄약·피해·건축물 파괴 | 벽 너머 피해·무한 발사·파괴 중복 보상 없이 견제 가능 |

## 8. 검증 목록

| 상황 | 기대 결과 |
| :-- | :-- |
| 먼 위치·영역 밖·허용되지 않은 종류로 설치 요청 | 설치 거절, 자원 변화 없음 |
| 두 플레이어가 같은 위치에 동시 설치 | 최종 결과에 맞는 1회 설치·비용 처리 |
| 자원이 마지막 1회분일 때 연속 요청 | 음수 자원·무료 구조물 생성 없음 |

| 엄폐물 뒤 플레이어 공격 | 규칙상 관통 무기가 아니라면 피해 없음 |
| 사망과 이탈·동시 피격 | 처치·전리품·파괴 보상은 1회 처리 |

건설 수 제한과 드롭 정리는 성능 측정 후 정한다. 단순히 구조물 수가 많다는 이유로 사용자가 올라가는 발판을 예고 없이 삭제하지 않는다. 모바일 대응은 사용자와 목표 기기를 정한 뒤 범위에 포함한다.

## 9. 다른 에이전트에게 전달할 사항

1. 새 미니게임의 Roblox 버전 계획이다. UEFN과 같은 핵심 규칙을 목표로 하지만 건설·전투 구현은 별도다.
2. 실제 Roblox 프로젝트·코드·자산은 아직 확인하지 않았다. 이 문서의 모든 체크리스트는 미완료다.
3. 사용자의 Studio·Luau 경험과 입력 기기를 확인하고 한 단계씩 안내한다. 요청받지 않은 프로젝트 코드를 임의 수정하지 않는다.
4. 먼저 사망·전리품·중간 상자·물 주기와 맵을 협의한다. 제안을 확정 규칙처럼 전달하지 않는다.
5. 최대 9명 개인전·최초 목표 높이 도달 우승을 유지한다. 2명 실험은 개발 검증 단계다.
6. 설치·피해·아이템 지급은 서버가 검사·확정한다. 클라이언트가 준 피해량·인벤토리 결과를 믿는 예제를 제시하지 않는다.
7. Fortnite 장치·Verse 코드·Unreal C++ 코드를 Roblox에 그대로 적용하지 않는다. 실제 Luau API로 검증한다.
8. 필요하기 전부터 파일·모듈을 과도하게 늘리지 않는다. 기존 코드가 생기면 먼저 읽고 안내한다.
9. UEFN에서 수정한 공통 규칙은 Roblox에도 비교·반영하되 플랫폼 전용 설정을 섞지 않는다.
