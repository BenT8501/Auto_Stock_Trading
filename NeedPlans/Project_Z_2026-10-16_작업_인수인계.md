## 4. 오늘 작업 요약

### 4.1 HUD 표시 문제 확인 및 수정

#### 증상

`CreateHUDWidget()`에서 다음 로그가 출력되고 HUD가 생성되지 않았다.

```text
[HUD] Controller = Project_Z_MultiPlayerController, Local = 1, HUDClass = None
[HUD] 1
[HUD] 3
```

#### 원인

- 로컬 컨트롤러 자체는 정상이었다.
- `HUDWidgetClass`가 `None`이었다.
- 멀티플레이 GameMode/PlayerController Blueprint의 HUD 클래스 연결이 필요했다.
- 기존 `ZStateHUDWidget`이 TPS 전용 PlayerController와 `AZCharacter_TPS`를 전제로 Pawn을 조회하고 있었다.

#### 적용 내용

- GameMode Blueprint에서 멀티플레이 PlayerController Blueprint 연결을 확인했다.
- PlayerController Blueprint에 HUD Widget Class를 지정했다.
- `UZStateHUDWidget::RefreshCurrentStatus()`가 `GetOwningPlayerPawn()`을 통해 Pawn을 얻고 `AZCharacterBaseMulti`로 캐스팅하도록 수정했다.

#### 사용자 확인

- HUD가 정상 표시됐다.
- HP와 탄약 표시를 확인했다.

### 4.2 공통 캐릭터 기능 정리

TPS에 종속돼 있던 다음 전투 공통 처리를 `AZCharacterBaseMulti` 중심으로 사용하도록 정리했다.

- 캐릭터 데이터 적용
- 현재 무기 데이터 복제와 `OnRep_CurrentWeaponData`
- 무기 메시 적용과 갱신
- 서버 발사 요청 및 Projectile 발사
- 서버 탄약 차감
- 서버 재장전 타이머
- 재장전 취소
- 발사·재장전 공통 애니메이션 실행
- Projectile 오브젝트 풀 획득

오브젝트 풀 시스템 자체를 BaseMulti로 옮긴 것은 아니다. `UZActorPoolSubsystem`은 독립적인 WorldSubsystem으로 유지하고, BaseMulti의 발사 코드가 이를 호출한다.

### 4.3 무기 데이터와 시각 컴포넌트 처리

무기 데이터는 Skeletal Mesh와 Static Mesh 중 하나를 사용할 수 있다.

- `EquippedWeaponMeshComponent`: Skeletal Mesh 무기
- `EquippedStaticWeaponMeshComponent`: Static Mesh 무기

두 메시가 무기 데이터에 동시에 지정되면 Skeletal Mesh를 우선 사용하고 경고 로그를 남기도록 정리했다. 사용하지 않는 컴포넌트는 메시를 비우고 숨긴다.

현재 소총 데이터는 실제 사용하는 메시 종류 하나만 연결해야 한다. 두 컴포넌트 중 아무 컴포넌트에나 직접 링크하는 구조가 아니라 `UZWeaponDataAsset`의 메시 필드가 기준이다.

### 4.4 발사·재장전 애니메이션 동기화

- 서버 발사 성공 후 `MulticastPlayAttackAnimation()`을 호출한다.
- 재장전 시작과 종료·취소 시 `MulticastSetReloadAnimation()`을 호출한다.
- 현재 무기 데이터가 복제되면 메시와 애니메이션 구성을 다시 적용한다.

발사 애니메이션 Multicast는 시각 효과이므로 `Unreliable`, 재장전 상태 애니메이션은 현재 `Reliable`로 구성돼 있다.

### 4.5 FPS 조준 방향과 Projectile 발사

FPS 캐릭터는 카메라 시점을 기준으로 조준 지점을 계산한다.

- Controller의 Player View Point에서 Visibility Trace를 수행한다.
- 카메라 Trace가 맞은 지점 또는 최대 사거리 지점을 조준점으로 사용한다.
- 실제 Projectile은 무기 총구에서 해당 조준점 방향으로 발사한다.

전투 판정은 Hitscan이 아니다. 카메라 Trace는 조준점 계산에만 사용하고, 실제 피해는 서버 Projectile 충돌에서 발생한다.

### 4.6 1인칭 전용 무기 Transform 데이터

공통 무기 위치를 변경하면 원격 플레이어의 무기 위치도 함께 변경되는 문제가 있어 1인칭 로컬 캐릭터 전용 데이터를 분리했다.

`UZWeaponDataAsset`에 다음 데이터가 추가됐다.

- `FirstPersonAttachLocationOffset`
- `FirstPersonAttachRotationOffset`
- `FirstPersonAttachScaleMultiplier`

`AZCharacter_FPS::ShouldUseFirstPersonWeaponTransform()`은 로컬 제어 캐릭터에만 위 보정을 사용한다. 원격 플레이어는 기존 공통 Attach Transform을 사용한다.

### 4.7 ADS 구현

FPS 캐릭터에 ADS 입력과 보간 처리를 추가했다.

- `ActionAim` 입력
- `StartAim()` / `StopAim()`
- 로컬 `bAimInputHeld`, `bIsAiming`
- 무기 위치·회전·스케일 보간
- 카메라 위치·회전 보간
- FOV 보간

무기 데이터에 다음 ADS 설정값이 추가됐다.

- `FirstPersonAimLocationOffset`
- `FirstPersonAimRotationOffset`
- `FirstPersonAimScaleMultiplier`
- `FirstPersonAimFieldOfView`
- `FirstPersonAimCameraLocationOffset`
- `FirstPersonAimCameraRotationOffset`
- `FirstPersonAimInterpolationSpeed`

사용자가 Blueprint 입력 연결 후 줌인·견착 동작을 확인했다.

### 4.8 Aim Offset 연결

BaseMulti에 다음 Blueprint 호출 함수를 추가했다.

- `GetAimPitchValue()`
- `GetAimYawValue()`

값은 `GetBaseAimRotation() - GetActorRotation()`으로 계산한다. 로컬 플레이어뿐 아니라 원격 플레이어도 Unreal Pawn의 복제된 View Pitch를 통해 Pitch 값을 얻는다.

Animation Blueprint에서 다음 흐름으로 연결했다.

1. `Get Owning Actor`
2. `Cast To ZCharacter_FPS`
3. `Get Aim Pitch Value`
4. `FInterp To`
5. AnimBP의 `AimPitch` 변수 설정
6. `AO_Rifle2`의 Pitch 입력
7. `Layered Blend Per Bone`으로 상체에 적용

`FInterp To`의 Delta Time에는 Anim Blueprint Update Animation 이벤트의 `DeltaTimeX`를 연결했다.

#### 사용자 확인 및 남은 제약

- AO_Rifle2 자체 동작은 확인했다.
- Alpha를 1.0으로 적용하면 1인칭 팔과 총이 화면에서 사라지거나 지나치게 변형됐다.
- Alpha를 낮추면 정상적으로 보인다.
- 현재는 낮은 Alpha를 유지한다.
- AO 강도, Blend Bone 및 1인칭 무기 위치는 나중에 조정한다.

## 9. 다음 작업 우선순위

### 가장 먼저 할 작업: 현재 전투 기능의 2인 회귀 테스트

새 기능을 바로 추가하기 전에 오늘 변경한 전투 흐름을 확정해야 한다. 이 검증이 실패한 상태에서 사망·리스폰을 추가하면 원인 구분이 어려워진다.

다음 순서로 호스트와 클라이언트 양쪽에서 확인한다.

1. 호스트가 클라이언트를 발사해 HP가 감소하는지 확인한다.
2. 클라이언트가 호스트를 발사해 HP가 감소하는지 확인한다.
3. 두 화면에서 HP와 탄약 값이 일치하는지 확인한다.
4. 장애물 뒤 대상에게 피해가 전달되지 않는지 확인한다.
5. 탄약이 0일 때 발사가 차단되는지 확인한다.
6. 재장전 중 발사가 차단되는지 확인한다.
7. 재장전 시작·완료·취소가 양쪽 화면에 표시되는지 확인한다.
8. 빠른 연속 입력에서 탄약 중복 차감이나 Projectile 중복 발사가 없는지 확인한다.
9. Projectile이 충돌 또는 수명 종료 후 풀에 반환되는지 로그와 화면으로 확인한다.

이 검증이 모두 통과하면 개발 2주차의 서버 전투 흐름을 완료 처리한다.

### 두 번째 작업: 사망 상태와 리스폰

전투 회귀 테스트 다음에는 연출이 아니라 사망·리스폰을 구현한다.

권장 순서는 다음과 같다.

1. 서버가 HP 0을 기준으로 사망 상태를 한 번만 확정한다.
2. 사망 상태의 저장 위치와 복제 방식을 결정한다.
3. 사망 시 이동·발사·재장전·상호작용을 서버에서 차단한다.
4. 진행 중인 재장전 타이머를 취소한다.
5. GameMode가 리스폰 시간을 관리한다.
6. 서버가 Pawn 재생성 또는 상태 초기화 방식으로 리스폰한다.
7. HP, 탄약, 입력, 이동 모드, 사망 상태를 초기화한다.
8. 호스트와 원격 클라이언트에서 사망·리스폰을 교차 검증한다.

현재 `bIsPlayerDead`는 일반 bool이며 명시적인 복제 속성으로 보이지 않는다. 다음 작업자는 이 값을 그대로 클라이언트 판단의 단일 근거로 사용하지 말고, 서버 권한 상태와 원격 표현 방식을 먼저 정해야 한다.

### 이후 순서

1. 사망·리스폰
2. GameMode·GameState·PlayerState 책임 분리
3. 팀 자동 배정과 팀 정보 복제
4. 팀별 PlayerStart와 리스폰
5. 접속·퇴장 및 최대 6인 관리
6. 6인·패킷 손실 검증
7. 설계와 오류 수정 기록 정리
8. 남은 시간이 있을 때 연출 튜닝

- 로컬 1인칭 무기 Transform과 원격 캐릭터의 공통 Attach Transform을 다시 하나로 합치지 않는다.
- 카메라 Trace를 사용한다고 해서 Hitscan으로 변경된 것은 아니다. 실제 피해는 Projectile 충돌에서 처리한다.
- ADS의 `bIsAiming`은 현재 로컬 표현용이다. 팀 또는 원격 상태 기능에 필요해지기 전에는 불필요하게 복제하지 않는다.
- Aim Pitch는 `GetBaseAimRotation()`을 기준으로 유지한다. 별도의 임의 replicated float를 추가하기 전에 기존 Pawn View Pitch 경로를 검증한다.
- 연출 문제가 보여도 기능 검증을 막지 않으면 일정 후반으로 넘긴다.

## 11. 내일 첫 작업의 완료 조건

내일 가장 먼저 수행할 2인 전투 회귀 테스트는 다음 조건을 모두 만족해야 완료다.

- 호스트와 클라이언트가 서로 발사하고 피해를 줄 수 있다.
- 장애물이 Projectile을 차단한다.
- HP와 탄약이 양쪽에서 일치한다.
- 탄약 0, 발사 간격 및 재장전 중 발사 제한이 서버에서 적용된다.
- 발사·재장전 동작이 상대 화면에 표시된다.
- 치명적인 중복 요청, 상태 불일치 또는 풀 반환 누락이 없다.
- 실패 항목은 재현 절차, 로그, 원인, 수정 및 재검증 결과를 기록한다.

위 조건이 통과하면 즉시 사망·리스폰 구현으로 이동한다.
