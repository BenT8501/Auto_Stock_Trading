## 3. 기초 학습 범위

| 항목 | 정리할 내용 | 완료 확인 방법 |
|---|---|---|
| 서버·클라이언트 | Listen Server의 호스트는 서버 역할과 로컬 플레이어 역할을 함께 수행 | 호스트와 원격 클라이언트의 실행 흐름 설명 |
| Authority | 서버 중심 설계에서 체력·탄약·사망의 최종 상태는 서버가 결정. Authority는 해당 Actor의 권한을 의미하며 로컬 조작 여부와 다름 | 각 캐릭터 인스턴스의 HasAuthority 로그 비교 |
| Ownership·로컬 제어 | 연결 소유 관계와 IsLocallyControlled의 차이, 소유 Actor를 통한 클라이언트의 Server RPC 요청 경로 | 캐릭터의 소유 관계와 로컬 제어 여부를 로그로 확인 |
| RPC | Server·Client·NetMulticast의 실행 대상과 호출 조건, Reliable·Unreliable 선택 이유 | 소유 캐릭터에서 서버로 테스트 요청 전달 |
| Replication·RepNotify | 서버 상태의 클라이언트 반영과 OnRep의 역할. 상태 복제는 모든 중간 변경을 이벤트처럼 전달하는 기능이 아님 | 서버 값 변경과 수신 값·OnRep 로그 비교 |
| 클래스 역할·수명 | 게임 규칙·플레이어 정보·캐릭터 전투 상태의 저장 위치와 리스폰·퇴장 시 처리 | 클래스 역할표와 상태 유지·초기화 표 작성 |

Reliable은 정상 연결과 유효한 호출 조건에서 전달 신뢰성을 제공하지만, 요청 내용이 올바르다는 보장은 아닙니다. 서버의 발사 조건 검증은 별도로 필요합니다. C++에서 서버가 복제 변수를 변경했다고 서버 자신의 OnRep가 자동 호출되는 것은 아니므로, 호스트 표시 갱신 경로도 함께 확인합니다.

### 학습용 테스트

1. 호스트·클라이언트, Actor 이름, HasAuthority, IsLocallyControlled를 구분할 수 있는 로그를 추가합니다.
2. 로컬 플레이어가 소유한 캐릭터에서 테스트 키 입력을 받습니다.
3. Server RPC로 테스트 요청을 전달합니다.
4. 서버에서 고정된 테스트 값만 변경합니다. 클라이언트가 실제 전투 피해량을 결정하는 구조로 사용하지 않습니다.
5. 복제된 값을 클라이언트에서 확인하고 OnRep 로그를 기록합니다.
6. 호스트가 요청한 경우와 원격 클라이언트가 요청한 경우를 각각 검증합니다.

```text
로컬 입력 → 소유 캐릭터의 Server RPC → 서버 값 변경
                                      ↓
                            클라이언트에 상태 복제
                                      ↓
                              OnRep에서 반영 확인
```

## 8. 서버 값 변경 테스트 결과 및 흐름

- 문서 반영일: 2026-10-01
- 대상: ZCharacterBaseMulti / BP_ZMultiCharacter
- 환경: 에디터의 2인 Listen Server 테스트
- 결과: **간단한 서버 값 변경 테스트 완료**
- 근거: 사용자가 [Input], [ServerChanged], [OnRep] 세 로그와 값의 정상 반영을 확인했다고 보고했습니다. 실제 소스 및 로그 원본은 본 문서에 첨부되지 않았으며, 아래 함수명과 예시는 안내한 코드 기준입니다.

### 처리 순서

1. 로컬 입력이 RequestTest()를 실행하고 [Input] 로그를 남깁니다. IsLocallyControlled()로 직접 조작하는 캐릭터인지 확인합니다.
2. ServerIncreaseTestValue() 호출은 Server RPC 요청입니다. 소유 클라이언트의 요청이 서버에 전달됩니다.
3. 서버의 ServerIncreaseTestValue_Implementation()에서 해당 캐릭터의 TestValue를 1 증가시키고 [ServerChanged]를 출력합니다.
4. ReplicatedUsing과 GetLifetimeReplicatedProps의 DOREPLIFETIME 등록에 따라 서버의 변경 값이 해당 Actor의 복제 대상 클라이언트에 전달됩니다.
5. 클라이언트의 TestValue가 갱신된 후 OnRep_TestValue()가 실행되어 [OnRep]로 수신 값을 확인합니다.

```text
클라이언트                               서버
RequestTest() / [Input]
    ↓
ServerIncreaseTestValue() ── RPC 요청 ──→ _Implementation()
                                           ++TestValue
                                           [ServerChanged]
                                                ↓
TestValue 갱신 ←──────── 프로퍼티 복제 ──────────┘
    ↓
OnRep_TestValue() / [OnRep]
```

서버와 클라이언트는 같은 메모리를 공유하지 않습니다. 각 인스턴스의 값을 네트워크로 맞추는 구조입니다. Server RPC는 요청을 보내고 프로퍼티 복제는 변경된 상태를 전달하므로, 복제 값은 RPC의 반환값이 아닙니다.

### 로그 판독 기준

아래 표는 실제 로그 인용이 아니라, 각 캐릭터의 초기값이 0일 때 첫 요청에 대한 예상 예시입니다.

| 입력한 플레이어 | 단계 | NetMode | Authority | Local | Value |
|---|---|---|---|---|---|
| 원격 클라이언트 | Input | Client | 0 | 1 | 0 |
| 원격 클라이언트 | ServerChanged | ListenServer | 1 | 0 | 1 |
| 원격 클라이언트 | OnRep | Client | 0 | 1 | 1 |
| 호스트 | Input | ListenServer | 1 | 1 | 0 |
| 호스트 | ServerChanged | ListenServer | 1 | 1 | 1 |
| 호스트 | OnRep | Client | 0 | 0 | 1 |

- Authority: 해당 Actor의 권한 여부. 서버의 원격 플레이어 캐릭터도 Authority=1입니다.
- Local: 해당 머신에서 직접 조작하는 캐릭터인지 여부. 서버의 원격 플레이어 캐릭터는 Local=0입니다.
- Value: 서버 변경 값과 이후 클라이언트 수신 값이 일치하는지 확인합니다. 캐릭터마다 값은 독립적입니다.
- 호스트 입력은 서버에서 RPC 본문이 실행되고, 이후 원격 클라이언트에 상태가 복제됩니다.
- C++ 서버는 직접 값을 변경해도 자신의 OnRep가 자동 호출되지 않습니다. 서버 로그는 변경 함수에서 출력합니다.
- 연속 변경 시 중간 값이 생략될 수 있으므로 OnRep 호출 횟수가 키 입력 횟수와 항상 같다고 가정하지 않습니다.

### 완료 범위와 남은 작업

완료한 것은 유효한 소유 캐릭터에서 요청하여 서버 값을 변경하고 클라이언트가 복제받는 기본 경로입니다. 계획서의 기초 단계 3일차에 해당하며, 네트워크 역할·RPC·Replication 학습 일부를 함께 확인했습니다.

다음은 아직 완료하지 않았습니다.

- 비소유 Actor의 RPC 요청, 연결 해제 등 예외 조건 검증
- 클래스별 역할·상태 수명 설계 및 기존 전투 코드 재사용 범위 확정
- 체력·탄약·사망·재장전 등의 실제 상태 복제와 서버 전투 판정
- 6인 및 패킷 손실 환경 통합 검증

테스트의 무조건 +1 처리는 학습용입니다. 실제 전투에서는 서버가 발사 조건과 명중을 검증한 뒤 체력·탄약을 변경하도록 확장합니다.
